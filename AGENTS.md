# Repository Guidelines

## Project Structure & Module Organization

This repository builds a Rust 2024 library, `reel_tui` (`src/lib.rs`), and one binary, `reel` (`src/main.rs`), on top of it. The library exists so integration tests under `tests/` can drive the same code the binary does. Keep responsibilities aligned across modules:

- `src/lib.rs`: Module declarations only; the crate root shared by the binary and the integration tests.
- `src/main.rs`: Entry point, worker spawning, terminal setup, and the top-level event loop. Deliberately thin — anything testable belongs in the library.
- `src/cli.rs`: Argument dispatch (`--help`, `--version`, the target directory) before the terminal is touched, so informational and usage-error output stays script-friendly.
- `src/config.rs`: The user's `config.toml` — worker-pool sizes, the desktop-notification switch, and the subtitle edit page's frame cache (`[preview] cache_tracks`, `[preview.prefetch] enabled`/`network`) and scrub playback (`[preview.playback] fps`/`pad`). `pad` is seconds as a float, so it is read through `Duration::try_from_secs_f64` — `from_secs_f64` panics on a negative, which a hand-written config file can hold — and NaN is rejected *before* the clamp, since `f64::min` answers with the other operand for it and a `pad = nan` would otherwise clamp to the maximum. `MIN_PLAYBACK_FPS`, `MAX_PLAYBACK_FPS` and `MAX_PLAYBACK_PAD` are public because the subtitle edit page's preview-settings popup adjusts the same two values for the session and must stop at exactly the limits a config file is held to, rather than at a second copy of them that can drift.
- `src/requirements.rs`: The external tool floors, enforced at startup. See **External Tool Floors** below.
- `src/input.rs`: Key handling (`handle_key` and friends): the mapping from a `KeyEvent` to an `App` mutation.
- `src/app.rs`: Application state, navigation layer management, probe/edit event dispatching, and persistent cache integration. Also holds `PreviewSettings`, which is both the subtitle edit page's cache policy *and* the five knobs the preview-settings popup (`:`) adjusts for the session — speed, loop, sound, padding, frame rate. **The popup mutates `PreviewSettings` in place and never writes to disk**: `config.toml` stays the defaults, `preview_defaults` keeps the copy `main` supplied, and `r`/`R` restore from that rather than from `Config::default()` — otherwise `r` on a user who set `fps = 24` would hand them 30 and look like a bug. The popup holds a cursor and nothing else, so what it shows is always what a playback would actually be done with rather than a copy taken when it opened; there is nothing to commit and nothing to discard. **No dialog may be raised over a running or decoding playback** (`App::playback_in_progress`): a span's pixels reach the terminal through its own image protocol rather than through the cell buffer a dialog is drawn into, so a popup opened over one is painted once and wiped by the next frame — open, swallowing every key, and invisible. There is no z-order that fixes this, so the two are kept apart instead: a dialog the user asked for is refused (`:` and `?` on the subtitle edit page), while one that raises itself — the conflict notice — stops the playback, since it cannot be refused. **The still frame is kept apart from a dialog by the same rule, drawn from the other end**: `render_edit_preview` leaves the picture out for as long as any dialog is up. The image widget writes its escape sequence into the pane's first cell and marks every other cell it covers *skipped*, and a skipped cell is never re-emitted by the diff — so a dialog that *shrinks while open* (a dropdown closing, the help panel going away) hands back cells nothing will ever paint over, and the border it drew stays on screen around the smaller dialog: the popup drawn twice, at two sizes. Opening and closing one was only ever safe by accident, because `dim_backdrop` restyles the cell the escape sequence lives in and so forces the picture to be re-sent; standing the picture down for the dialog's whole life extends that to every shape it takes in between. Do not "fix" this by drawing the image under a dialog again — the artifact is invisible to `TestBackend`, since the halfblocks protocol the harness uses writes ordinary cells and skips nothing, which is why `a_dialog_over_the_preview_should_take_the_picture_down_rather_than_sit_on_it` asserts the *rule* (no image cells while a dialog is up) rather than the artifact.
- `src/staging.rs`: Staged edits and in-flight batch state (`StagedEdit`, `BatchState`), the shape a save is dispatched and reported through.
- `src/ui.rs`: Ratatui rendering, split layout rendering, stream detail popups, and status indicators (including `[NET]` badge). The subtitle edit page's cue panel draws one *group* to a row rather than one cue — `render_edit_group` and `render_edit_fork`, and **Cues That Share The Screen Are One Row** below. `timeline_lines` draws **every cue the same way, whatever the track's density**. A dense typeset track is made readable by shortening the window it is drawn in (`TimelineWindow::fitted`), never by demoting the cues the cursor is not on: a version that drew only the selection's overlapping neighbours as spans and the rest as dim rules was tried and rejected, because where every other line begins and ends is most of what the pane is worth reading for. Crowding is a scale problem here, not an emphasis problem. `axis_tick` picks the ruler's interval from the window's length (`TICKS`, `TICK_TARGET`) rather than always ten seconds, because a shortened window with a ten-second interval can carry one reading or none once the selection's `▲` marks take the column it would have gone in — an axis with no numbers on it is not an axis. **`axis_columns` is the single answer to where a tick is**, read by the ruler that labels one and by `timeline_lines`, which rules a dashed `┊` down every lane at each of them: a gridline under no reading is merely unlabelled — the ruler drops one that would crowd its neighbour or paint through a mark — but a gridline *beside* a reading would be the axis contradicting itself, which is what deriving the columns twice eventually produces. The gridlines are painted before the cues, so a bracket, the playhead and the cursor each win their column back; dashed rather than the solid `│` those last two use, because three vertical bars separated only by colour is one distinction too many for a pane read at a glance that can carry all three at once. **The background pass's `[done/total]` count sits on the cue panel's own border** (`render_edit_cues`), right-aligned opposite ` Cues `, rather than on the status row: it counts that panel's rows, and on the status row it occupied the page's one message slot for the whole of a long pass — hiding the messages that are about what the reader is doing right now. `group_timing` is the one decision that has to be taken for a whole track rather than per cue: it measures the track's widest reading against half a panel and picks the compact span or the start alone, so the column never changes shape halfway down the list. The preview-settings popup reuses the shared `SettingsDialog` with no text entry and no help panel, and marks a row as *changed* when it differs from what `config.toml` asked for. Speed, padding and frame rate are `setting_line` plus the same `dropdown_line` children every other settings popup opens, so `Enter` opens and commits and `Esc` backs out one level. **The two switches are `toggle_line` instead**, because both answers fit on the row and opening a list to choose between them would hide the answer in order to ask the question; `Enter` flips it and `h`/`l` pick the left or right button (setting rather than flipping, so key repeat lands somewhere instead of oscillating). `h`/`l` are bound *only* there — on a dropdown row a value is chosen from a list, the way it is in every other settings popup. `toggle_line` is built from `action_option`, the button component the three confirm dialogs already use; that takes a `Style` rather than a `focused` flag so both kinds of row can style their buttons through `choice_style`, which is where a button, a dropdown row and a field value all agree on what "chosen", "changed" and "inert" look like. **Every list in this popup runs descending** — fastest, longest, highest first — and `PlaybackSpeed::STEPS` is stored in that order too, because one order for the data and the display is what stops the list and the cursor disagreeing about which end is which. `K` opens the same help panel the other settings popups have (`preview_field_help_text`); its five rows make it the shortest dialog in the application, so it is the one a long explanation overruns first — `every_help_text_should_fit_the_panel_it_is_drawn_in` covers it along with the rest. `playback_settings_badge` puts the same answer in the preview pane's *title* (`Preview · 0.5x · loop · muted`) rather than on the subtitle edit page's status row, which already carries one message at a time and where "Preparing playback…" is the one worth reading while a span decodes. It names only speed, loop and sound: padding and frame rate change what a playback costs rather than what it looks like, and a title listing all five would be longer than most panes are wide.
- `src/files.rs`: Directory scanning, file tree nesting, and adaptive filesystem monitoring.
- `src/framecache.rs`: The on-disk cache of rendered preview frames, at `$XDG_CACHE_HOME/reel-tui/preview_frames/{media_key}/{cue_key}.jpg`. Content-addressed with 128-bit FNV-1a: `media_key` covers the media file, its length and mtime, the size frames are rendered at, and `CACHE_FORMAT_VERSION`; `cue_key` covers the **staged subtitle file** — the exact bytes handed to libass — and the cue's timing, which the staging is retimed away from. Not the cue's text: two ASS cues can read the same words in different styles and draw differently. An edited cue simply misses and is re-rendered, with no invalidation logic anywhere. **The two-level path is the eviction policy, not tidiness.** What the user opens is a *track*, and a track missing some of its frames is re-rendered on every visit, so the unit of eviction has to be the unit of use: `prune(tracks, open)` deletes whole media directories, least recently used first, and never the open one. Ranking is by the `.used` marker's mtime (`touch`), so a fully cached track — the ideal case, where the pass renders nothing — does not age out under tracks rendered once. The directory *is* the index, which keeps the grouping without a side file to corrupt or a lock to take. Bump `CACHE_FORMAT_VERSION` when a stored frame stops meaning what it did; that orphans whole directories which then age out, instead of leaving files whose names collide with live keys. `migrate` is the one exception to "the key is the whole truth": a save remuxes the file, which moves its length and mtime, and the frames the page just rendered would be orphaned by the edit that page itself started — so the caller that performed the rewrite moves the directory onto the new key. Whole directories, for the same reason `prune` evicts them that way. Frames are **JPEG** (`FRAME_EXTENSION`), not PNG: ~90 KB at 1080p against ~2 MB for a *smaller* PNG. Resolves its directory through `DiskCache::cache_dir()`, never from the environment, so both test redirections apply. Pure filesystem and hashing.
- `src/probe.rs`: Asynchronous `ffprobe` worker thread, media metadata parsing, and tuned probing flags (`-probesize`, `-analyzeduration`).
- `src/edit.rs`: Asynchronous `ffmpeg` remuxing, track reordering, container conversion, progress reporting, cancellation, and cross-filesystem transaction publishing (`move_or_copy_file`).
- `src/subtitle.rs`: Subtitle stream inspection, sidecar file matching, format conversion, language tag translation, and OCR/libass capability detection (`ToolCapabilities`). `ToolCapabilities` tracks `ffmpeg_decoders` separately from `ffmpeg_encoders` because the subtitle edit page *reads* where the rest of the program *writes*, and a build ships plenty of one without the other. `preview_blocked(format)` is the subtitle edit page's pre-flight gate: it refuses before the page opens, so a missing tool reads as a refusal naming the tool rather than a page that loads, sits on its loader, and fails. `CueEdit`, `CueSnapshot` and `rewrite_srt_cues` are the cue editor's and the timing mode's half — see **Editing a Cue Is a Staged Edit Like Any Other** and **Moving a Cue Through Time Is a Mode, Not a Dialog** below.
- `src/cue.rs`: Cue-level subtitle data — SubRip and ASS parsing into individual cues (`parse_srt`, `parse_ass`), timeline lane packing, and the mapping from cue times to terminal columns. ASS parsing also yields the `AssScript` header its cues are drawn by, and `retimed_dialogue` rewrites one cue's line for the preview's staged file. Also `collapse`, which folds the several events that draw one line into one cue (**One Visible Line Is One Cue** below), and `on_screen_at`/`on_screen_between`, which answer **what a viewer sees** rather than what one cue says (**A Frame Is The Whole Screen** below). `group_overlaps` is the third of that family and the coarsest: it splits the cue list into the runs that share the screen, which is the unit the cue panel draws (**Cues That Share The Screen Are One Row** below). A run reaches from its *furthest* end rather than its last cue's, so a sign covering a scene keeps every line spoken under it in one group; `<` rather than `<=` at the boundary, the same one `pack_lanes` draws, since a cue starting exactly where the last ended is never on screen with it and treating it as though it were would group most of an ordinary dialogue track into one run. `format_compact` is the timing that fits half a cue panel, between `format_timestamp` and `format_clock` in what it spends — it keeps the tenth of a second and gives up the leading zeroes, and takes `with_hours` from the caller for the reason `format_clock` does. Both take the anchor's *position in the slice*, not its `Cue::index`: the two agree for a parsed track, but a list whose indices had drifted would pull in every cue sharing the anchor's index instead of the anchor. `TimelineWindow::fitted` picks how much of the track the timeline shows: it walks `WINDOW_STEPS` down from a minute until the cues in the candidate window fit the lanes' columns (`READABLE_CUE_COLUMNS` apiece), because a minute of a typeset track holds several hundred events and fills every lane end to end with brackets. **Never shorter than the selected cue plus half again**, or a long sign would be clamped at both edges and drawn as a bar with no ends — legibility of the selection outranks legibility of its company. The choice follows the track's measured density rather than its format, so a sparse ASS track keeps the full minute and a dense SubRip one does not. No dependency on `App`, `ratatui`, or subprocesses.
- `src/subtitle_edit.rs`: State for the subtitle edit page (`SubtitleEditState`): which cues a track holds, how they group into rows (`groups`, from `cue::group_overlaps`), which cue is selected, the small window of frames encoded and ready to draw (the selected cue and up to `NEARBY_FRAMES` either side — `window_radius()` is the actual reach, see below), how far the background frame pass has got (`WarmState`), why a frame cannot be drawn at all (`PreviewSupport`), and the scratch directory that is released when the page closes. Also which of the page's two panes holds the cursor (`EditFocus`) and, when that is the timeline, where the cursor stands and the one frame drawn for it — see **The Timeline Cursor Is a Second Focus, Not a Second Selection** below. **`PreviewSupport` and `frame_error()` are split by permanence, and the split is the point**: a condition that cannot change while the page is open (this FFmpeg cannot burn subtitles in, or the terminal has no image protocol) is a `PreviewSupport` reason drawn in the preview pane, while a single cue's render failure is `frame_error()` on the status row. Putting a per-cue failure in the pane would reintroduce the text that flashed there on every cursor move, which is why `frame_error()` is keyed on the selected cue rather than exposed as a field. **The window is budgeted, not fixed**: `window_radius()` takes `NEARBY_FRAMES` as a ceiling and shortens it to fit `preview::FRAME_WINDOW_BUDGET`, because a `Protocol` holds the bytes the terminal is going to be sent rather than the picture — kitty and iTerm2 hold the frame's pixels as base64 RGBA and sixel about a byte a pixel (`preview::frame_bytes_per_cell`), which is tens of megabytes for a full window on a large pane. Floored at one either side: a window of nothing puts the worker round trip back on every cursor move, which is what the window exists to remove. `prune_frames`, `nearby_frame_targets`, and `has_missing_nearby` all use the same radius, or the page would render frames it immediately discards and ask for them again. **The panel's cursor moves in two axes and they are not the same thing**: `select` steps whole *groups*, while `select_within_group` is `h`/`l` and stops at the group's ends. **A group is re-entered where it was left** — `group_memory` keeps each visited group's cue and page, so `j` down a row and `k` back returns to the cue that was under the cursor rather than to the group's first member; without it, one press of `k` cost several presses of `l` to undo. A group never visited is entered on its first member, and `gg`/`G` are absolute moves that land where they say and overwrite the memory rather than leaving it stale. A `j` from a later member of the last group is refused rather than obeyed — the group step has nowhere to go, and moving to that group's first member would answer "down" by going up. `group_window` derives which two members are drawn from the selection rather than storing a second cursor: the group is cut into pages of `GROUP_COLUMNS` and `group_page` says which one is drawn, so the pair holds still while the cursor crosses it and only moves when the page turns, backing up at the group's end so two are shown there too. **`cue_scroll` takes a height in rows, not a count**: a lone cue is three rows and a group six, so how many rows a screenful costs depends on which groups are in it and there is nothing left to divide. Also holds the scrub playback (`PlaybackState`, `Playback`), whose one subtlety is **which page movements stop it**: the cursor landing on another cue, the cue being retimed under the span (`set_cue_timing`) and a new track arriving all do, because a span playing under a line it is not about — or under a timing that line no longer has — reads as the timing being wrong; a *pane resize* does not, and must not — announcing the playback is what puts "Preparing playback…" on the status row, and that row comes out of the preview pane's height, so a playback stopped by a resize is stopped by the act of saying it is starting, every time, on any page whose background pass has finished. The frames absorb it instead: they hold pixels, and `Playback::advance` encodes for whatever cell area the pane has become. **`Playback::position` multiplies by the span's speed**, because frames are `1 / fps` apart in *output* time and the playhead answers in *media* time — without the factor the mark on the timeline would crawl at the speed the picture is playing at and read as the cue being mistimed, which is the one thing this page must never say wrongly. A looping playback re-opens its `AudioSource` and resets to frame zero where a non-looping one returns `PlaybackStep::Finished`; the frames are already in memory, so a repeat runs no `ffmpeg`, and a span holding no frames still ends rather than opening a device per iteration of the event loop forever.
- `src/preview.rs`: The subtitle edit page's four background workers — reading a track's cues (see **Subtitle Formats the Subtitle Edit Page Reads** below), grabbing the video frame at the selected cue with that cue burned in plus encoding the cues either side of it from the cache (`FrameRequest`'s `wanted` and `nearby`), the frame at whatever moment the timeline cursor stands on (`ScrubTarget`, never cached, no `subtitles` filter when nothing is on screen there), and rendering the rest of the track's frames behind them with scoped threads over contiguous slices — half the machine's cores, floored at 1 and capped at `MAX_WARM_WORKERS` (3), because a fixed three cost the *interactive* grab +157% latency on a dual core. **Each warm worker stages its cue under its own name** (`warm_cue_file(n)`, distinct from the interactive `CUE_FILE`): two sharing one staged `.srt` would overwrite each other between the write and the burn, and the frame would carry another cue's line under the right cache key — invisible to any assertion about keys, counts or files, which is why the tests for it compare rendered bytes. Frames are rendered at a fixed size derived from the source, capped at 1080p by `MAX_FRAME_PIXELS` (not the pane's size, which changes), and cached through `framecache.rs`. The grab is `mjpeg -pix_fmt yuvj420p -q:v 2`; the pixel format is load-bearing, since the mjpeg encoder refuses the limited-range YUV most video actually is. The fourth worker is the scrub playback: one `ffmpeg` decodes a whole span straight to raw `rgb24` (an accurate seek costs the same whether one frame comes out of it or four hundred), with the sound as a second output of the *same* pass so picture and sound describe the same stretch of media by construction. Three things there fail invisibly: `scale` is a literal `W:H` with **no** `force_original_aspect_ratio`, because the output is sliced by `width * height * 3` and a frame one row short shears every frame after the first rather than cropping — the proportions are kept by `playback_cells` choosing the size from the source's aspect ratio instead; the cue is staged by `CueStyle::stage_between` at its place *inside* the span rather than covering it, which is the opposite of what the still grab wants and which every assertion short of the pixels still passes; and the sound goes to a **file**, not a second pipe, since two pipes into one `ffmpeg` deadlock the moment either reader falls behind — which means every playback of a page writes the same name in the same workspace, so a run that asks for no sound (muted, or media with no audio track) must both **clear that file before the decode and skip reading it after**, or the page plays the *previous* cue's sound under this one's picture. Playback frames are never cached — `framecache` keys on a cue and evicts whole tracks, and a run of frames keyed on time has no business in it — so the frame rate is what gives when a span will not fit in `PLAYBACK_BUDGET` (`affordable_fps`), since span length and terminal size are the user's. **`PlaybackSpeed` is applied entirely by that one decode** — `setpts` on the picture, `atempo` on the sound — which is what keeps the two describing the same stretch of media and leaves `audio.rs` knowing nothing about speeds. Three details there are load-bearing and none of them is visible in a frame count: `setpts` sits *behind* `subtitles`, because libass lays the text out against the source's own timestamps and a retimed stream moves the cue out from under the frames it belongs on, and *ahead* of `fps`, so the rate filter yields that many frames per second of output rather than per second of media; a quarter speed emits `atempo=0.5,atempo=0.5`, since one filter cannot halve a span twice and `ffmpeg` refuses `atempo=0.25` outright; and `affordable_fps` is charged the **stretched** span (`span / speed`), or a slow playback quietly overshoots the budget by the speed factor. **`source_capped_fps` runs before that budget**, because the `fps` filter *duplicates* frames to reach a rate the source does not hold: a 24 fps film asked for 60 comes back two and a half times the size for the same picture, and the waste is charged to `PLAYBACK_BUDGET` as if it were real. Scaled by the speed for the same reason the budget is — a second of output covers `speed` seconds of media, so half speed has half the source's frames to give it — and skipped entirely when ffprobe will not state a rate, since guessing one would make a playback choppier for a file that was merely unreadable. **The popup is capped by the same ceiling** (`App::playback_fps_choices`, `effective_playback_fps`): a dropdown offering a 23.976 fps track sixty frames a second states a rate that cannot happen and gives the reader no way to tell. **The list is capped at the speed-scaled ceiling, so it shortens as the speed drops** — a 24 fps film offers 24/15/10/5 at normal speed and 6/5 at a quarter of it. Leaving the full list there would offer four rows that all play identically, which is the same defect as offering 60 on a 24 fps film one level down; the list getting shorter is the honest signal, not a side effect. The ceiling is rarely one of the curated rates, so `effective_playback_fps` is *merged* into the list rather than only filling in an empty one — it is what the row will play at, so it has to be selectable and `preview_choice_cursor` has to be able to find it. The row is never disabled, because a rate *below* the ceiling is still a real choice at any speed: it is the escape hatch for a terminal that cannot keep up over ssh or inside tmux, which is exactly where slow playbacks live. The *setting* is left alone by both caps, so a detour through quarter speed — or a visit to a 24 fps film — does not cost the user the 60 they chose. One consequence worth knowing: with the list capped this way, slowing a playback down costs no extra memory at all, since `(span / speed) x fps` is at most `span x source_fps` whenever `fps` is under the ceiling. At exactly normal speed neither filter is emitted, so the default command is byte-identical to the one this was added to. **The span is decoded at `playback_pixels`, which is the terminal's own cell size per cell, taken off the picker.** The frame is then drawn as pixels through that same picker — which is the only way a burned-in subtitle is *readable* rather than merely present. There is no cells-and-colours fallback anywhere in this path, and there must not be: `preview::drawing_picker` refuses a halfblocks picker at startup (see **Previews Require a Real Image Protocol** below), so a page that exists is a page that can draw.

**`playback_cells` and `playback_pixels` apply the cell's aspect ratio in opposite directions, and the two must cancel.** A cell is roughly twice as tall as it is wide, so a 16:9 picture is nothing like 16:9 *in cells*: `playback_cells` divides by that ratio to pick the cell area, and `playback_pixels` multiplies it back by the font to pick the decode size. Both take the ratio from the font rather than from a constant two, which is what makes the product come back to the source's proportions exactly — a cell that is 8x17 rather than a tidy 10x20 would otherwise stretch every frame by a seventeenth. Dropping either factor, or applying one twice, distorts the picture by about four and no assertion about counts, keys or command lines notices. Because they cancel, `PlaybackFrames::pixels` *is* the picture's true shape, which is what a resize re-fits against; there is no separate record of the media's own size and none is needed. The three figures that do have to agree — `pixels`, `cells`, `picker` — are gathered into `SpanShape` and travel with the span, so the decode resolution and the encoder are provably one decision. That is also why the playback worker clones the picker inside `spawn_preview_workers`' `Some(picker)` arm: a decoded span without a picker to draw it with is then not a state that exists. Deliberately does **not** route through `edit.rs`, so a read-only preview never writes `edit_errors.log`.
- `src/audio.rs`: Sound for the subtitle edit page's scrub playback, and the clock the picture is driven from. **The sound is the clock**: nothing schedules a frame, the audio device is asked where it has got to and the frame index is derived from that (`frame_index_at`), so there is no second clock to drift against. **Counting the samples written to the device is the wrong clock and the mistake this module exists to prevent** — a callback fills a buffer the device plays one period later, so a written-sample counter *leads* the sound by the device latency: constant, silent, tens of milliseconds, and indistinguishable on screen from the subtitle actually being early. `PlaybackClock::anchor` therefore takes cpal's `playback`-minus-`callback` lead and re-anchors every callback, leaving wall time to interpolate across one buffer period. `PlaybackClock` names no audio library, which is what lets the part that has to be right be tested on a machine with no sound card. `SilentOutput` is **production code, not a test double**: a machine with no device and media with no audio track take it, and the tests get it because it is that path — and so does a playback the user muted, which asks for no sound from the decode at all rather than turning a device down. `AudioSource` is the second seam, and it exists for looping: a `cpal` stream plays its buffer once, so going round again means opening another output rather than rewinding one. `subtitle_edit::Playback` therefore holds a source rather than an output, and a repeat costs a device open rather than another `ffmpeg` run. The one thing in here that cannot be tested through a device is `span_slice`, hence its being a function — `handed_over` counts whole buffers of device *time* rather than samples copied (freezing it at the last sample walks the reported position backwards), so it runs past the end of the span, and `slice[n..n]` panics for `n` past the end even though the range is empty.
- `src/notification.rs`: Best-effort desktop notifications when a save finishes while the terminal is unfocused.
- `src/mount.rs`: Network mount detection via `/proc/mounts` (NFS, SMB/CIFS, SSHFS, Rclone, Ceph, etc.) and `REEL_NETWORK_MODE` environment variable overrides.
- `src/cache.rs`: Persistent on-disk probe metadata cache (`DiskCache`) stored at `$XDG_CACHE_HOME/reel-tui/probe_cache.json`.

Unit tests live beside their implementation in `#[cfg(test)] mod tests` blocks. End-to-end tests live in `tests/e2e.rs` with helpers in `tests/e2e/`. Release publishing is defined in `.github/workflows/publish.yml`.

## End-to-End Test Suite

`tests/e2e.rs` drives the real application: it replays the `main.rs` event loop in-process, feeds synthetic `KeyEvent`s through the same `handle_key`, renders through the same `ui::render` into a `TestBackend`, and runs genuine `ffprobe`/`ffmpeg` subprocesses against real files. Nothing in the crate is mocked; only crossterm's terminal setup and byte decoding are bypassed.

- It is a **separate cargo test target with `test = false`**, so ordinary `cargo test` does not run it; use the restricted execution rules below.
- **Comprehensive e2e coverage is the target, and the current gaps are testing debt to fill incrementally.** Whenever work touches a functional area that lacks an overarching scenario in `tests/e2e.rs`, add one as part of that work.
- **Every new or materially changed functional behavior must be covered by at least one overarching scenario in `tests/e2e.rs`.** The scenario must exercise the behavior through the real application workflow independently of module-local unit tests and make meaningful assertions about the observable result. Coverage overlap is explicitly welcome and does not waive either layer. Purely visual styling or layout changes do not require their own e2e scenario, but do require focused rendering/unit coverage.
- **Tests never skip.** Do not use `#[ignore]`, conditional early returns, environment-based success paths, or any other mechanism that reports an unexecuted test as passing. Required programs, codecs, language data, and other external capabilities are test-environment prerequisites; fail immediately with an actionable missing-prerequisite message.
- **E2E execution is deliberately restricted.** Run an individual scenario only while creating or directly changing that scenario. Run the complete e2e suite only once as the final verification immediately before merging a branch. Do not run e2e tests during ordinary implementation, routine verification, or on every edit. Minutes of wall clock for the final suite is fine: use real codecs, containers, subprocesses, and OCR rather than reducing fidelity for speed.
- When a regression scenario comes from a failure in `~/.cache/reel-tui/edit_errors.log`, quote that log line in its doc comment. That log is the first place to look when hunting for an edit regression worth locking in; UI and workflow regressions need not originate there.
- Fixtures are built by `tests/e2e/fixtures.rs` over `lavfi` sources, parameterised by codec and container. Codec/container realism is the point: the bugs this suite exists for come from combinations like `subrip` into MP4 or `mov_text` into Matroska, which the simpler `ffv1`/`pcm_s16le` unit fixtures cannot express.
- **Scenarios that render preview frames must take `harness::frame_cache_lock()`.** `XDG_CACHE_HOME` is process-global, so every scenario in the binary renders into one frame cache, and the subtitle edit page prunes that cache to whole media directories at the start of every background pass — `a_full_cache_should_evict_whole_tracks_and_never_the_open_one` deliberately prunes it to a single track. Run in parallel without the lock, the scenarios delete each other's frames: one walking a cue list waits forever for a frame another has just evicted, which reads as a hang in the feature rather than as interference. It is not a wall-clock cost — taking it took the suite from 92 s to 18 s, because the thrashing was re-rendering evicted frames.
- The harness redirects `XDG_CACHE_HOME` to throwaway storage, so runs never touch the user's real probe cache or failure log. The unit-test binary is covered separately: `DiskCache::cache_dir()` returns throwaway storage under `cfg(test)` (`src/cache.rs`). **Both halves are load-bearing** — without them a test run rewrites `~/.cache/reel-tui/probe_cache.json` with `/tmp` fixture paths and fills `edit_errors.log` with deliberately-failing test edits, which is exactly the log this file tells you to read first. Never add a test that resolves the real cache directory.
- **Write tests that would notice.** A test that passes against broken code converts an unchecked path into a checked-looking one, so assert the observable result rather than the fact that something ran. A feature-level e2e scenario need not reproduce every defect in that feature; focused regression coverage belongs in the unit suite.

## Subtitle Formats the Subtitle Edit Page Reads

Every format ends at the same place — a SubRip file `cue.rs` parses — and differs only in how it gets there. `preview::prepare` owns the dispatch; `ToolCapabilities::preview_blocked` refuses the rest before the page opens.

| Format | Road to the cue list |
| --- | --- |
| SubRip | `-c:s copy` out of the container, or the sidecar read where it lies. Parsed by `cue::parse_srt`. |
| ASS | **Also `-c:s copy`, and that is load-bearing** — see below. Parsed by `cue::parse_ass`. |
| WebVTT, MOV Text | Transcoded to SubRip — on the way out of the container for an embedded track (`-c:s subrip`), in a second `ffmpeg` pass for a sidecar. Needs an `ffmpeg_decoders` entry, not an encoder one. |
| TTML, PGS, VobSub | Refused. TTML has no FFmpeg decoder at all (there is an encoder, which is not the same thing); PGS and VobSub carry pictures rather than text. |

**ASS is never transcoded, because a transcode discards what makes previewing it worth doing.** An ASS cue *names* a style rather than carrying one, and positions itself against the script's declared `PlayResX`/`PlayResY` rather than against the video. So the page keeps three things a SubRip track has no equivalent of:

- `Cue::dialogue` — the cue's original `Dialogue:` line(s), verbatim. `Cue::text` is what the *reader* needs (markup stripped, `\N` unfolded) and this is what the *renderer* needs; for ASS they are not the same string. A `Vec`, because several events that draw one line are folded into one cue — see **One Visible Line Is One Cue**.
- `CueStyle::Ass { header, events_format }` — the file's `[Script Info]` and `[V4+ Styles]` verbatim, plus the `[Events]` `Format:` line. Field order is declared per file rather than fixed by the format, so both the parse and `cue::retimed_dialogue` read that line rather than assuming the usual columns.
- `CueSlot` — the staged file's *name*, whose extension libass picks its reader from. A staged ASS script called `.srt` is read as SubRip and every override tag in it lands on the frame as literal text.

**`framecache::cue_key` hashes the staged file, not the cue's text.** That is what makes the key provably complete: the picture is a pure function of the media, the moment seeked to, and the file handed to libass — `media_key` covers the first, the cue's timing covers the second, and the staged bytes cover the third. Hashing the text was right while SubRip was the only format, where text *is* the staged file; it stops being right the moment two cues can read the same words in different styles and draw differently.

**The staged filename and the extraction's `-c:s` have to agree.** `ffmpeg` picks its muxer from the extension, so a WebVTT track transcoded to SubRip and written to `cues.vtt` fails on a codec the muxer will not take. `extracted_format` is the single answer both halves read, and the mistake is invisible in either half alone — which is why an e2e scenario covers it rather than only a unit test of the command.

**Test the styling on rendered bytes.** A preview that lost an ASS track's styling still parses the right cues, caches the right number of frames, and draws the right list — every assertion short of the picture passes. `an_ass_track_should_preview_with_its_own_styles_rather_than_libass_defaults` therefore gives two cues identical words in different styles and compares the cached JPEGs, the same reason the warm-worker staging test compares bytes.

## External Tool Floors

`src/requirements.rs` holds the minimum versions, each measured rather than guessed. Do not lower one without re-measuring; each is load-bearing.

- **FFmpeg 8.1** (`ffmpeg` *and* `ffprobe`) — enforced at startup, refusing to launch below it. `n8.1` is the first release containing FFmpeg commit `e59d964a3c`, which taught the `mov` demuxer to read the ISO-BMFF `name` atom. Below it `ffprobe` reports MP4/MOV track titles as absent, so a remux erases every title, `apply_edits` writes the erasure out as `title=`, and `validate_result` compares absent against absent and passes it. No flag works around it — the muxer never receives a title the demuxer did not parse. The e2e suite otherwise passes on 5.0.1 through 8.0.1, so the floor is entirely about this. Also verified green on **9.0.1**, the whole suite, so the major version bump needs no ceiling.
- **seconv 5.1.0** — gates subtitle conversion and OCR, not startup. 5.0.0 cannot read a VobSub `.idx` ("Unable to determine subtitle format"). **Cannot be version-gated**: the 5.1.0 build reports `5.0.0` from `--version`, so `subtitle::seconv_is_supported` probes the `--help` listing for `--no-vobsub-isolate-colors` instead. Also needs `libicu` present, or it aborts in `Bootstrap.Initialize`.
- **Tesseract 4.0** — gates OCR only. Verified working on 4.0.0, 4.1.1, and 5.3.x. 3.x is unreachable regardless: `seconv` needs a newer glibc than any distribution shipping it.

- **`pkg-config` and the ALSA headers** — a *build* dependency, not a runtime one, and not versioned. `cpal` pulls in `alsa-sys`, whose build script is a bare `pkg_config::probe_library("alsa")`, so without them the crate does not compile and no suite runs at all. A machine with the headers but no sound *device* is fine: `audio::open` falls back to `SilentOutput`, which is the same production path a user without a sound card takes, so CI needs no audio hardware.

CI installs these from `.github/actions/media-tools`, never from the runner's distribution packages — `ubuntu-latest` ships FFmpeg 6.1.1, which is below the floor. `.github/workflows/ci.yml` runs both suites on every push and pull request to `main`; `publish.yml` runs on release tags only and is not a substitute for it.

## Editing a Cue Is a Staged Edit Like Any Other

`i` on the subtitle edit page opens the cue editor (`App::open_cue_editor`, `Dialog::EditCue`) on the selected cue. It is a **multi-line buffer of its own** rather than the application's `TextInputState`: a SubRip cue is routinely two lines and where it breaks is part of what the reader is judging, so a single-line field would quietly turn every two-line cue into one. The popup is the largest in the application and does not wrap, because a line long enough to wrap is a line the reader should see is too long.

- **SubRip only, and the refusal says so.** An ASS cue names a style and positions itself against the script rather than carrying its own appearance, so editing the stripped text the list shows would either throw the styling away or need an editor that understands override tags.
- **Leaving the editor keeps the typing** (`Esc`), the way leaving vim's insert mode does; `Ctrl+S` stages it and starts the save. The *editor* discards nothing, so the popup never has to raise a second dialog over the one page that cannot hold two (see `App::playback_in_progress`) — throwing the work away is a decision taken on the way off the page instead, where it is asked about once for all of it.
- **The edit is staged, not written** — `SubtitleChange::cue_edits`, so it travels with every other staged edit through `staged_edits`, `has_track_edits`, the conflict machinery and the batch. `Ctrl+S` writes it, from the subtitle edit page as from anywhere else.
- **Addressed by position, checked against the whole cue.** A cue has no identity in the file, so `CueEdit` keys on its position in the parsed list and carries a `CueSnapshot` of what the file said; `subtitle::rewrite_srt_cues` re-parses the file it is about to rewrite and refuses when the cue standing at that position is not the one the reader was looking at. Without the check, a sidecar edited in another program between staging and saving would have the new text land on whichever line moved into the slot. **The snapshot covers the words *and* the timing, and both halves are checked**, because each fails invisibly on its own: a cue retimed elsewhere still says what the reader read, so a text-only check would drop their edit onto a line that has already moved. Editing a cue back to what the file says stages nothing at all, and a second visit keeps the *file's* snapshot rather than the last edit's.
- **One entry per cue, not one per kind of change** (`App::stage_cue_edit`). A cue is what the reader edits, what the border counts and what leaving the page discards, so a second map keyed the same way would have to be kept in step at every one of those places — `changes_media`, `has_effect`, `staged_cue_edits`, `discard_cue_edits` and the two gates in `edit.rs` — and at every one added later. It is also what makes a future global shift or framerate stretch a different way of filling the same map rather than new plumbing: **the edit stores the result, not the operation.**
- **A sidecar is rewritten in place; an embedded track goes through the remux.** The sidecar publication lists the original in `remove` even though the new file lands on the same name — that is what makes it a replacement rather than an export, so the transaction backs it up first and `resolve_export_duplicates` (which renumbers exports onto `.1`/`.2`) leaves it alone. An embedded track is copied out with `-c:s copy`, rewritten, and mapped back in as a `SubtitleReplacement`, which is the mechanism a format conversion already uses. Cue edits are applied to the file *first*, so a track that is also being converted or imported carries the new words into whatever it becomes.
- **Leaving the page discards the cue edits, and asks first** (`Dialog::ConfirmLeaveCues`, `App::discard_cue_edits`). This page is the only place staged cue text is visible, so carrying it out of here would leave the reader with words they cannot see, no way back to them short of returning, and a Ctrl+S from anywhere else that writes them. The question exists because the answer is destructive; a bare `Enter` takes the safe half (`LeaveCuesChoice::StayHere`). **Only the cue text goes** — a conversion, a language tag or an export staged from the track list was never visible here, so `discard_cue_edits` clears `cue_edits` and stores the change back through `store_subtitle_change`, which drops the entry outright when nothing is left of it rather than leaving an empty one that makes the file look modified. The cue panel's border carries the count (`N edited`) for the same reason the question is asked, in the corner the background frame pass uses while it runs.
- **An edited row says so in its own words**, yellow and italic (`render_edit_cue`) — the pair every other staged-but-unwritten thing in the application wears. The count on the border says how many were rewritten but not which, which on a track of a thousand cues is no answer at all. On the selected row only the italic survives: the cyan fill owns the colours there, and yellow on cyan is unreadable.
- **The save comes back to the page** (`SubtitleEditReopen`, `App::reopen_subtitle_edit`). Writing rewrites the file the page is reading, so the page is closed and the file re-probed — but the reader asked to save a cue, not to leave. The request is remembered rather than the layer: which track, which cue, and which file it *became*, since a container conversion renames it. Dropped rather than deferred when the reader has moved to another file, when the track is gone, or when a page is open already — a request held forever would spring a page open later on something unrelated. It fires from `receive_probe_results`, because there is nothing to draw until the re-probe lands.
- **The frames already rendered survive the save** (`framecache::migrate`, `App::move_frame_cache`). An embedded track is written by remuxing, which moves the file's length and mtime — both in the frame cache's media key — so without this, saving one word orphans every frame of the track and the page re-renders all of them, on every save. The remux copies the video stream through untouched, so the directory is moved onto the new key instead. **The claim lives with the caller that performed the rewrite, not in the key**: `frames_survive_edit` refuses a re-encoded video (`video_settings`) and a video track removed or reordered against another, and anything it does not recognise. Baking a remux-surviving identity into `media_key` would mean guessing which rewrites preserve the picture, and a wrong guess serves one file's pictures for another's — the worst thing this page can do.

## Moving a Cue Through Time Is a Mode, Not a Dialog

`t` on the subtitle edit page turns the timing mode on (`SubtitleEditState::timing_mode`, `App::toggle_cue_timing_mode`). In it, `h`/`l` shift the selected cue by `subtitle_edit::TIMING_STEP` (50 ms), `H`/`L` by ten of them, and `r` puts the cue back to the timing the file gives it (the same thing `r` does to a focused field on the track list). Refused on a non-SubRip track for the reason the editor is, which is one reason stated once (`CUE_EDITS_SUBRIP_ONLY`): an ASS cue's timing is the anchor every `\move`, `\fad` and karaoke tag in it is measured from, so shifting the cue without shifting them animates the line against itself.

- **A mode rather than a dialog, because no dialog may be raised over a playback** (`App::playback_in_progress`) and the work this is for is alternating a nudge with a `p` until the line lands. It is therefore the one timing-page action *not* gated on `playback_in_progress()`. It is sticky and follows the cursor, so `j`/`k` still walk the track and a whole file can be retimed without turning the mode on again at every cue.
- **A nudge stops a running playback**, and this is not the same as the mode being useless during one. A span is decoded ahead of time with the cue already burned into its frames, so one still playing after a nudge is playing the timing the reader has just moved away from — "a span playing under a line it is not about", which `select_cue` exists to prevent. Re-decoding instead would be an `ffmpeg` run per keypress.
- **Both ends move by the same amount, even at the floor.** A cue near 0:00 stops moving with its duration intact rather than being shaved a little on every press, which would be a nudge silently editing something the reader did not ask it to. A press that would move nothing reports `None`, so the caller stages nothing and a held `h` at the floor does not re-render a frame per repeat.
- **More frames go stale than the cue's own** (`set_cue_timing`). A frame is burned with every cue on screen at that moment, so moving one line into or out of a neighbour's moment changes what the neighbour's picture should show. Every encoded frame overlapping the cue's old *or* new span is dropped (`cue::shares_screen`, which is also `on_screen_between`'s rule so the boundary is defined once). Clearing the whole window would be correct too and costs a decode per neighbour on every press of a held key.
- **The lanes are repacked and the groups deliberately are not.** `LaneLayout` is computed once rather than per draw, so a moved cue would otherwise keep being drawn in a lane that no longer describes it. The overlap *groups* are the unit the panel's cursor and scrolling are measured in, and recomputing them under a held key would reflow the list around a keypress already resolved against the old one — the hazard `apply_prepared` cites for not deriving them per draw. A collision a nudge creates still shows, in the repacked lanes.
- **`Esc` peels the mode off before the page, and after the playback** (`App::back`). The playback comes first because the two are meant to be used together: an `Esc` aimed at a span that is playing must not also cost the reader the mode they were nudging in.
- **The timing mode swaps two colours rather than adding a third** (`selection_colour`, `playhead_colour`). The selected cue is normally cyan and the playhead yellow, chosen that way because they must not be the same; in the mode the selection takes yellow — what everything staged-but-unwritten wears — and hands cyan to the playhead. Painting the selection yellow alone would put a yellow `│` inside a yellow span, and that pair is on screen exactly when a reader nudges a cue with a span still playing. The ruler's `▲` marks follow the selection for the same reason, or "which cue am I on" is answered in two colours at once.
- **The timeline's title is the readout** (`format_shift`): the cue's live times plus how far it has moved, `Timeline (00:00:05.1 → 00:00:07.1 · +0.15s)`, and yellow while the mode is on. Neither half is enough alone — without the times the reader cannot see where the cue now is, and without the shift they cannot tell three presses from six. Dropped rather than shown as zero for a cue at its own timing, and hundredths rather than the tenths the timestamps carry, since a tenth-second readout would sit still for every other press of a fifty-millisecond step. **It is stood down entirely while the timeline holds the cursor** — see the cursor's own readout below.
- **`h`/`l` lose their other meaning while the mode is on**, and that is the accepted cost of the keys: moving between cues that share a moment comes back with `Esc`. It is bounded, since this is a SubRip-only feature and overlapping SubRip cues are uncommon.
- **The file is re-sorted on write, after the edits are applied** (`rewrite_srt_cues`). A cue nudged past its neighbour must leave the file in time order, and the positions the edits are keyed by address the file as it was read — so the sort can only happen once every edit has landed. `cue::write_srt` renumbers from one for free.

## The Timeline Cursor Is a Second Focus, Not a Second Selection

Everything else this page can draw is anchored to a cue: the still lands on the moment a cue comes in (`preview::seek_for`), and a playback covers a cue's span plus padding. So the one question the page could not answer was "where does this line *actually* belong", whose answer is a moment no cue names. `Ctrl+J` therefore hands the page's cursor to the timeline pane (`subtitle_edit::EditFocus`, `App::focus_timeline`), `h`/`l` walk it by `TIMELINE_STEP`, `H`/`L` by ten of those and `Ctrl+H`/`Ctrl+L` by `TIMELINE_FINE_STEP`, and the preview pane shows that moment with whatever a viewer would see there burned into it. `Ctrl+K` takes the cursor back. Nothing is edited by any of it — it is a way of looking.

- **A focus, not a mode.** The pane holding the cursor owns the keys that mean movement in it, which is why `h`/`l` mean three different things here and the focus settles it *before* the timing mode does, and why `j`/`k`, `gg`/`G` and `Ctrl+D`/`Ctrl+U` are inert while the timeline holds the cursor — it has no vertical axis for them to move along. They are swallowed by one arm in `input.rs` rather than by a guard on each, so a movement key added later cannot quietly start walking the cue list under a reader who is looking somewhere else. The timing mode is deliberately left alone by a focus change: scrubbing to a frame and then `Ctrl+K`-ing back to nudge a cue onto it is the workflow this exists for.
- **Three scales, one movement.** `move_cursor` takes the step size from the caller rather than reading a constant, so the fine step, the ordinary one and the leap are the same code at three sizes and every rule below — the clamp, the playback it stops, the `false` it reports at either end — holds for all of them by construction rather than by three copies agreeing.
  - The ordinary step is **ten times the cue nudge's, and that is not an oversight**: a nudge is aimed at a mouth movement, where fifty milliseconds is about as fine as the eye can judge, while the cursor is aimed at a *shot*, and at fifty milliseconds a minute of film is twelve hundred presses.
  - `Ctrl+H`/`Ctrl+L` are **exactly the cue nudge** (`TIMELINE_FINE_STEP = TIMING_STEP`), which is the point rather than a coincidence. The coarse step finds the shot and this one finds the frame inside it, and the workflow the pane exists for is scrubbing onto the frame a line should land on and then nudging the cue there — so a cursor that could stand between two nudges would point at a timing no number of presses can reach. Bound with a modifier because bare `h`/`l` already carry three meanings on this page and none of them could be given up.
- **The cursor is re-seeded on every entry, from `seek_for` of the selected cue.** Arriving in the pane then changes what the keys mean and nothing else, because the moment it lands on is the one the preview is already showing — which is also why entering asks for no grab at all, and why `render_edit_preview` falls through to the selected cue's frame when there is no cursor frame yet. A remembered position would come back pointing wherever the reader last left it, which after a few `j`s is nowhere near what they are looking at.
- **Its frames are never cached, and that is the same rule the scrub playback follows.** `framecache` keys on a cue and evicts whole media directories, so a run of pictures keyed on time would compete with the track's real frames for the unit of eviction. The consequence is that every settled position costs an accurate seek, so the request is *always* debounced (`scrub_request_due`) where a cue's is only debounced when it would have to be rendered — and the previous moment's picture is **kept on screen until a newer one lands**, because blanking the pane between them would flicker on every press of a held key. The timeline's title states the moment the cursor is really on throughout, so the pane is never the only thing speaking (see the title bullet below). A grab that *fails* does drop the picture, since a pane showing one moment while the status row explains another is the page contradicting itself.
- **A moment with nothing on screen is grabbed with no `subtitles` filter at all** (`frame_command`'s `Option<&str>`). Most of a film has no subtitle on it and the cursor reaches those moments constantly; staging an empty SubRip file instead would hand libass a file its demuxer rejects, failing a grab that has nothing to burn. What *is* staged comes from `cue::on_screen_now` — `on_screen_at` without the forced anchor, because a moment the reader pointed at is already where they want to look and forcing a cue onto it would draw a line the viewer would not see.
- **It travels as its own field and comes back as its own event** (`preview::ScrubTarget`, `FrameRequest::scrub`, `PreviewEvent::ScrubFrame`, `CueSlot::Scrub`). A moment has no cue index to be filed under, and borrowing one would collide with a real cue in the page's frame window and in the cache. `newest_frame` carries a coalesced-away `scrub` forward exactly as it carries `wanted`, and for the same reason: the page clears the request the moment it hands one over, so one dropped here is a pane that never catches up with the cursor.
- **The window slides to hold the cursor rather than re-centring on it** (`TimelineWindow::containing`). Re-centring would move the whole track under a cursor that moved half a second, so nothing on the timeline would stay still long enough to be read against anything; this holds the picture still until the cursor reaches an edge and then scrolls with it.
- **The scroll position becomes the reader's the moment the timeline takes the cursor** (`SubtitleEditState::window_start`, `TimelineWindow::starting_at`). `fitted` anchors a window on the *selected cue* and is rebuilt from it on every draw, so sliding that the minimum needed to hold the cursor pinned the cursor to whichever edge it had left by, on every frame — and coming back the other way then dragged the whole track underneath a cursor that never moved off the edge. The remembered start is restored first and `containing` runs on *that*, which is what makes the cursor travel across the window and reach an edge before anything scrolls. Only the start is remembered: the length still comes from `fitted` per draw, because the pane's width and the track's density decide it and both can change mid-scroll. `None` until the first draw of a visit, so arriving changes nothing on screen, and `None` again on leaving, so a later visit is an arrival rather than a return to a position the cue list has since moved away from. The one place that knows both how long a window is and where this one ended up is the drawing code, which is why it writes the start back — `render_edit_timeline` takes `&mut` for that and nothing else. `starting_at` is deliberately unclamped; see its doc comment.
- **Green, because there is no spare shade of the other two.** Cyan and yellow are the selected cue's and the playhead's, and they *swap* between those two in the timing mode — a reader nudging a cue with a span playing and the cursor parked elsewhere has all three on screen at once. The cursor is a `│` painted over everything including the playhead, since it is the one mark on the pane they are actively moving, and a `▼` on the ruler whose column is reserved before the readings are placed, exactly as the selection's `▲` marks are. `focus_border` moves between the cue panel and the timeline so there is something on screen saying which pane `h` is about to talk to.
- **The title reads for one pane at a time, and the cursor's reading stands bare.** With the cursor in the timeline the title is `Timeline (00:00:07.20)` and nothing else: the cue's times and its shift are stood down, because they answer a different question from the one the reader is moving and three timestamps in a row that changed shape with the focus made them work out which two belonged together before they could read either. Nothing is lost — the cue's own times are on its row in the panel throughout. Hundredths (`cue::format_precise`) rather than the tenths every other display format uses, since the fine step is fifty milliseconds and tenths would sit still for every other press. No `▼` in front of it either: with one reading at a time there is nothing for a glyph to tell it apart from, and the mark belongs on the ruler where it names a column.
- **`Esc` peels it after a playback and before the timing mode.** After the playback because the two are independent and a span may well be running while the reader scrubs; before the timing mode because the cursor is the more recent of the two states they are holding.

**Assert this on the picture.** Every layer short of the pixels agrees whether or not the grab really moved: the cue list is untouched, the frame cache is untouched, and the request differs only in one `-ss`. `the_timeline_cursor_should_preview_a_moment_no_cue_points_at` therefore puts one cue in the white stretch of a clip that turns black-to-white two seconds in, walks the cursor back to 0:00, and reads the brightness off the pane.

## One Visible Line Is One Cue

**A `Dialogue:` event is not a line; it is a brushstroke.** A typeset or karaoke line is routinely a dozen events sharing a timing and a set of words, each carrying a different override tag so that together they animate. Before `cue::collapse` the subtitle edit page listed a dozen rows that were identical in every way a reader can see — same words, same timestamps — and each previewed a fraction of the picture. So both parsers end with `ordered`, which sorts, folds and *then* numbers: folding after numbering would leave indices addressing rows that no longer exist.

**The fold test is deliberately dumb: identical start, identical end, identical text, and adjacent in the file.** Rows indistinguishable to the reader become one row and nothing else is touched. Anything looser starts guessing which of a file's events belong together — real karaoke gives each syllable its own timing, and merging those would hide the very differences this page exists to show. A run broken by an interloper that merely shares the timing is *not* rejoined, for the same reason. The rule is about cues rather than formats, so a SubRip file that repeats a line at the same moment collapses too.

The folded cue's own timing needs no thought precisely because of that test: every member shares it. What is kept from each member is its `Dialogue:` line — the only thing they differ in — which is why `Cue::dialogue` is a `Vec<String>` rather than an `Option<String>`, and why `CueStyle::staged` stages *every* line of every cue. Drop any of them and the preview shows a fraction of the effect, which is the defect the fold exists to remove rather than to reintroduce. The sort is stable, so the members keep the file's order, which is the order libass draws them in.

`Cue::events` counts how many of the file's entries a row stands for, and `render_edit_cue` puts `×4` on the right of its top border when that is more than one — without it the fold is silent, and the list simply has fewer rows than the file has entries with nothing on screen to say why. Counted rather than read off `dialogue.len()`, which holds a line only for ASS: a folded SubRip row has no lines to count and still stands for two entries. The count is **dropped outright when it and the timing would not both fit**, because ratatui does not arbitrate between overlapping titles — the right-aligned one simply paints over the left, and a wide count on a narrow panel would leave a plausible, wrong end time on screen. The fit is measured on what the two titles *say* plus a column between them, since their decorative edge spaces can share a column harmlessly.

Because the fold happens in the parse, nothing downstream needed to learn about groups: one row, one frame, one cache entry, one span to play, one timeline block. `events_that_draw_one_line_should_be_one_row_end_to_end` checks all five at once, since a fold that reached only the list would leave the cursor on a row whose preview and playback still belonged to one event.

## A Frame Is The Whole Screen

**A cue is not what the viewer sees; the cues on screen together are.** A typeset or karaoke line is routinely one visible line split across a dozen `Dialogue:` events that share a timing and differ only in their override tags — each drawing part of one effect, the picture being the sum of them. Burning the selected one on its own draws a fraction of a picture nobody will ever see, on the page whose whole job is judging a subtitle against the picture. The same holds, less dramatically, for a sign over a line of dialogue.

So every burn stages a *group*, from `cue::on_screen_at` (an instant, for the still grab) or `cue::on_screen_between` (a stretch, for the scrub playback). Three things follow and each is load-bearing:

- **The anchor is included whether or not it passes the test.** `seek_for` holds a grab back from the very last instant of the media, so a cue running to the end of the file is sampled just outside itself — filtering on the instant alone would burn in every cue on screen *except* the one being previewed, which is a blank preview for the last line of every track.
- **The cache key covers the company, not just the cue** (`FrameSource::key(cue, on_screen)`). Both halves fail in opposite directions: keying on the staged file alone gives two cues sharing a moment one frame filed under the first one's name; keying on the cue alone serves a picture drawn without the lines over it. Two cues with identical timings *and* an identical group legitimately share one entry — they are one picture.
- **The background pass builds its group from the whole cue list, never from its own slice** (`WarmSlice::offset`). The lines sharing a cue's moment are wherever the file put them, and a slice boundary falling between them would have a warm worker render a different picture from the interactive grab — under the same cache key, so whichever ran first would win and nothing downstream could notice.

**The instant a still is grabbed at is the moment the cue comes in** (`preview::seek_for`), held back only from the very end of the media. The midpoint stood there first and answered a different question: it shows a frame the line is comfortably on top of, which says nothing about whether the line arrived with the shot — and arriving late is visible at the cue's start and nowhere else in its span. Grabbing exactly at the start is safe only because the burn window below stretches every staged cue across it; at their own timings, a seek landing a rounding error early would draw nothing at all, which is precisely the frame being aimed at. `framecache::CACHE_FORMAT_VERSION` was bumped for the change, since the cache key covers the cue's timing and that did not move.

The still grab retimes every cue in the group to cover the whole burn window, because a still is sampled at one instant and the burn must not turn on the rounding; the cost is that an animated line is frozen at whatever phase that window puts it in. The playback does the opposite and must: `stage_span` shifts every cue by the *same* amount — the span's start — so the gaps between them survive the rebase and an effect built from staggered lines plays as the effect rather than as a dozen lines arriving at once. A cue that began before the span is clamped to its start, since an ASS timestamp cannot be negative.

**Test this on rendered bytes.** Every assertion short of the picture passes against the broken version: the cue list is the same, the cache holds a frame per cue, and the commands differ only inside a staged file. `a_cues_frame_should_show_everything_on_screen_with_it` gives two cues the same words, style and duration over a constant black frame and puts an overlay over only the second, then compares the JPEGs — and separately asserts that the two cues sharing a moment produce *identical* frames, which they did not before, when they were complements.

## Cues That Share The Screen Are One Row

**The cue panel used to draw two cues that are on screen together exactly as it drew two that merely follow one another**: a block, an arrow, a block. On the page whose whole job is judging a subtitle against the picture it is burned into, the one relationship worth seeing was the one the list could not express. So `cue::group_overlaps` splits the list into runs that share the screen, and the panel's unit of drawing, scrolling and movement is that run rather than the cue. The ordinary cue overlaps nothing, is a group of one, and is drawn exactly as it always was — full width, full `00:00:05.0 → 00:00:07.0` timing, `↓` to the next row.

A group is a drawn fork into two blocks side by side, the later-starting one a row lower.

- **Two blocks, never three, and that is forced rather than chosen** (`subtitle_edit::GROUP_COLUMNS`). The panel is thirty to forty-eight columns, so two blocks get fourteen to twenty-three each and a third would get ten to sixteen — which cannot hold a timing at all, and a block with no timing on this page has nothing worth reading on it.
- **A grouped block cannot carry the full timing either.** Twenty-three characters do not fit twenty-three columns once the block's own borders are taken, at any terminal size. `group_timing` picks `0:05.0→0:07.0`, or the start alone where even that will not fit — a thirty-column panel, or media past the hour, which needs roughly a hundred and fifteen columns before the span fits. **Decided once for the whole track**, measured against the last cue's end since the list is start ordered: a column that changed shape halfway down would make the reader work out which format they were looking at before they could read the number.
- **The step down says which member comes in first, and the case carrying the information is the one where it is not taken.** Cues arrive start-ordered, so the step is always downward to the right and adds nothing to the left-to-right order — except when two members start at the same instant, are drawn level, and the panel is saying "these appear together" rather than "this one comes in after". The fourth row is charged either way, so `h` and `l` move through a group without the list reflowing underneath.
- **The fork belongs to the group rather than being the connector into it**, which is why a group costs six rows and not four. Drawn that way it survives every scroll position, including the group being the first thing on screen — and the fork's crossbar is what says the group reaches past its two visible members: it runs off the panel's edge on that side, with a `┬` over the outer block, so the eye reads a line continuing past the wall rather than a marker to be decoded. A sign that vanished when the list happened to scroll would be worse than none at all. The one exception is a panel too short to hold both: `render_edit_group` drops the fork below five rows, because at the smallest size `render` allows the cue list gets two rows and a fork drawn into them would leave the cue under the cursor off screen entirely.
- **`j`/`k` and `h`/`l` are two axes and must stay different things.** `j` steps over a whole group; `h`/`l` move inside one and stop at its ends. Letting `l` spill into the next group would make holding it walk the track sideways, and the two axes would collapse into one. Coming back to a group is not a fresh arrival, though: `k` returns to the member the cursor was left on.
- **Sideways movement pages rather than slides.** `group_window` cuts the group into runs of `GROUP_COLUMNS` from its first member and draws the run named by `group_page`, so `l` from a page's left member moves the highlight across the pair standing still and only the press after that turns the page. A window anchored on the cursor moved both blocks on every press, so no two cues ever stayed still long enough to be compared — which is the whole point of drawing them side by side. **The page is kept in the state rather than derived from the selection**, because the last page backs up to keep two members drawn and so a middle member belongs to two pages: derived, `h` from the right-hand block of a backed-up page turned the page instead of moving to the block beside it, jumping the cue the reader was pointing at off the row. `select_within_group` turns the page only when the cursor leaves it, and the page is remembered with the cue when the cursor leaves the group altogether (`group_memory`) — so `k` back into a group restores the pair it was left in, and a group the cursor has left keeps drawing that pair rather than snapping back to its first members, which the reader would watch happen one row up as they press `j`. A group entered for the first time lands on its first member, on page zero.

**Two quick sideways presses exposed a frame-delivery race that predates all this**, and `preview::newest_frame` is the fix: the page clears its frame request the moment it hands one to the worker, so a `wanted` discarded by the worker's coalescing was a preview pane that stayed empty until the cursor happened to move again. The answers to the first press's request set `refill_nearby`, whose dispatch carries no `wanted` of its own and lands behind the second press's grab. A discarded grab is now carried forward onto the request that replaced it, which is only ever reached when that request has none — precisely the case where the page believes its earlier grab is still on its way.

## Previews Require a Real Image Protocol

The subtitle edit page exists to judge a subtitle against the picture it is burned into, so a terminal that cannot show the picture cannot answer the question the page is for. `preview::drawing_picker` therefore discards a `Halfblocks` picker at startup, in `main.rs`, and `spawn_preview_workers(None)` follows from that: no frame worker, no background cache pass, no playback. The page still opens and still reads the cue list — that half works — and says `PreviewSupport::NoImageProtocol` in the preview pane rather than leaving it blank, since silence there is indistinguishable from a slow render.

This matters because `Picker::from_query_stdio` reports halfblocks for *every* terminal that answered nothing, so without the refusal the fallback would be the common case: full-screen terminals rendering, caching and playing hundreds of frames that arrive as coloured mush, with the user judging subtitle timing by them. Two coloured half-cells cannot carry text. Terminals that do work are those offering kitty graphics (kitty, Ghostty, WezTerm, Konsole), iTerm2 (iTerm2, WezTerm, Konsole, mintty), or sixel (foot, WezTerm, mlterm, xterm, contour, Windows Terminal).

**The e2e harness deliberately passes a halfblocks picker anyway** (`Harness::start`), because it is the only protocol `TestBackend` records as cells with symbols and colours — kitty, sixel and iTerm2 write escape sequences the buffer never stores, so no assertion could see the picture. Everything the page does with a frame is protocol-agnostic; only the encoder differs. `Harness::start_without_image_protocol` is the other side, and `a_terminal_with_no_image_protocol_should_say_so_rather_than_draw` is what holds the refusal in place.

## Adaptive Filesystem & Performance Architecture

`reel-tui` automatically detects whether the target directory resides on a local disk or a remote network mount (NFS, SMB, etc.):

- **Directory Monitoring**: Local directories use a 1-second reconciliation interval; network mounts use an adaptive 10-second interval to eliminate network stat thrashing.
- **Persistent Probe Cache**: Media metadata is cached on disk in `$XDG_CACHE_HOME/reel-tui/probe_cache.json` indexed by path, file length, and mtime. Opening `reel` on network shares loads previously probed files instantly.
- **Fast Probe Flags**: Remote media probing uses `-probesize 2000000 -analyzeduration 3000000` to prevent deep network seeking.
- **Local Scratch Remuxing**: When remuxing on network mounts, intermediate work files write to local fast storage (`/tmp/reel-tui-scratch`) before performing a single final stream publish to destination.
- **Preview Frame Cache**: Opening the subtitle edit page renders every cue's frame in the background and caches it on disk, so revisiting a cue — or re-opening the page — costs a decode rather than an `ffmpeg` seek. Bounded by whole media files (`cache_tracks`, default 10) rather than by bytes, because a byte budget can bisect a track and half a track is re-rendered on every visit. Off by default on network mounts, where a feature-length track is a thousand-odd accurate seeks across the network; the page says so in its status row rather than leaving the absence unexplained.
- **Ready Preview Frames**: On top of the disk cache, the page keeps the selected cue's frame and the ones either side of it *encoded* in memory, so moving the cursor draws a picture in the same pass that handled the keypress rather than after a round trip to the worker. `FRAME_DEBOUNCE` therefore applies only to a cue that would have to be rendered — one already in the frame cache is asked for immediately, since it costs a file read rather than an accurate seek. **A debounced cue is held back from the dispatch, not the dispatch itself**: the neighbours travelling with it are cache-only by construction, so returning early would strand the cheap work behind the expensive work and hand back the round trip the window exists to remove. `clear_nearby_request` is what makes that safe — the held-back grab is deferred, not answered, and still goes out when the debounce expires. In the other direction, `apply_warming` refills only when `has_missing_nearby()`, since the background pass reports ten times a second and a full window has nothing to fetch. That gate is deliberately **not** "has the pass reached the window": the warm workers render contiguous slices in parallel, so `done` counts frames rather than describing a prefix. The preview pane draws nothing when it has no frame; it never substitutes the cue's text, which flashed on every cursor move. The one exception is a preview that can *never* work — no libass, or no image protocol — which the pane says once and keeps saying, since silence there is indistinguishable from a slow render.
- **Environment Overrides**: Set `REEL_NETWORK_MODE=1` (or `0`) to manually force or disable network performance tuning.

## Build, Test, and Development Commands

- `cargo run`: launch the TUI against the current directory. Ensure `ffmpeg` and `ffprobe` are available in `PATH`.
- `cargo build`: compile a debug binary.
- `cargo build --release`: compile an optimized release binary.
- `cargo install --path .`: install or replace the `reel` executable in `~/.cargo/bin/reel`. Always run this after making changes.
- `cargo test`: run all module-local unit tests. Excludes the e2e suite.
- `cargo test --test e2e <scenario> -- --exact`: run one scenario only while creating or directly changing that scenario.
- `cargo test --test e2e`: run the complete end-to-end suite only as the final pre-merge gate. Its required `ffmpeg`/`ffprobe` programs and encoders must be installed; missing prerequisites fail the suite.
- `cargo fmt --check`: verify standard Rust formatting.
- `cargo clippy --all-targets -- -D warnings`: run strict linting used by CI. Note this does **not** cover `tests/e2e.rs`, whose target sets `test = false`; lint that one with `cargo clippy --test e2e -- -D warnings`.
- `cargo publish --dry-run`: validate packaging without publishing.

## Coding Style & Naming Conventions

Use `rustfmt` defaults (four-space indentation) and keep Clippy warning-free. Follow Rust conventions: `snake_case` for functions, variables, and modules; `PascalCase` for structs and enums; `SCREAMING_SNAKE_CASE` for constants. Prefer small, responsibility-focused functions and propagate recoverable failures with `anyhow::Result`. Preserve terminal cleanup guarantees and keep blocking `ffmpeg`/`ffprobe` work off the UI event loop.

**No inline control help text**: never add a hint/help line (e.g. "↑↓ select · Enter apply") to a dialog, popup, or view's render function, no matter how new or small. All keybinding help lives solely in the global keybindings popup (`?`, `Dialog::Keybindings`/`keybindings_text()` in `src/ui.rs`). If a new view's keys aren't already covered by that popup's generic entries, extend `keybindings_text()` rather than adding local hint text.

## Testing & Reinstallation Guidelines

Add tests in the module affected by the change, using descriptive behavior names such as `cancelled_edit_preserves_original`. Use temporary paths for filesystem cases and deterministic JSON fixtures for probe parsing. No test in any suite may be ignored or conditionally skipped. During ordinary work, run `cargo fmt`, `cargo clippy --all-targets -- -D warnings`, and `cargo test`; reserve the complete e2e suite for the final pre-merge gate.

### Coverage and Regression Policy

- Maintain a project target of at least **90% measured line coverage**, and prefer coverage comfortably above 90%. Measure branch coverage as well when the installed Rust coverage tooling supports it, and improve weak branch coverage rather than relying on the line percentage alone.
- New or modified production paths must have **100% line and branch coverage from module-local unit tests**. E2E coverage is a separate requirement and does not substitute for unit coverage. Existing uncovered code remains debt, but touching it means covering the affected paths completely.
- Every bug fix must include a focused module-local regression unit test that fails before the fix and passes afterward. Reproduce the complete failure mode, including effects on neighboring or untouched data; do not test only the value directly changed by the user. The affected functional area must also have an overarching e2e scenario; add one if it does not, but that scenario need not reproduce the exact defect.
- Cover meaningful success, failure, cancellation, validation, and transaction/rollback paths. For FFmpeg and ffprobe behavior, include integration tests using small deterministic media fixtures when unit tests cannot verify the real command semantics.
- Treat coverage as a diagnostic floor, not proof of correctness. Do not inflate it with assertion-free tests, broad exclusions, or tests that execute code without validating observable behavior. **Covering unreachable code is inflation too**: before writing a test to reach the coverage bar, check that the application can actually reach the path. If it cannot, delete the path instead of testing it, and say so.
- Report the unit-test coverage method and totals with completed ordinary changes. Report merged unit-and-e2e coverage only at the final pre-merge gate. If coverage cannot be measured in the current environment, state that explicitly rather than estimating it.
- **Measuring final pre-merge coverage.** Branch coverage needs `-Z coverage-options=branch`, which only nightly `rustc` accepts, so it runs under `cargo +nightly llvm-cov --branch`. Because the unit and e2e suites are separate targets, the merged commands below run the complete e2e suite and therefore must only be used immediately before merging a branch:

  ```sh
  cargo +nightly llvm-cov clean --workspace
  cargo +nightly llvm-cov --no-report --branch            # unit tests
  cargo +nightly llvm-cov --no-report --branch --test e2e # e2e suite
  cargo +nightly llvm-cov report --branch --summary-only
  ```

  A plain `cargo llvm-cov` run silently excludes the e2e suite (its target sets `test = false`), which understates `edit.rs` in particular — the remux paths it covers are the ones only e2e reaches.

  Do **not** set `LLVM_COV`/`LLVM_PROFDATA` to the system `/usr/bin` binaries for these runs: the Arch system LLVM is older than nightly's and fails with `raw profile version mismatch`. Rustup supplies matching `llvm-tools` for the toolchain automatically. (That override was only needed back when the machine had no rustup at all.)

  Note that `llvm-cov` counts branches inside `#[cfg(test)]` modules as well as production code, so a test containing loops or `match`es raises the denominator along with the numerator. Treat the per-file trend, not the absolute percentage, as the signal.

**Mandatory Reinstall Step**: After making changes and successfully passing tests, ALWAYS run `cargo install --path .` so the updated `reel` binary is immediately installed to `~/.cargo/bin/reel`.

### Edit Progress Contract

Treat accurate progress reporting as a required part of every Save workflow change. Every blocking subprocess, potentially slow filesystem operation, validation pass, transaction phase, rollback, and cleanup path must emit a concise typed progress phase immediately before doing the work. Use measured phase-local progress only when the underlying operation exposes reliable units; otherwise show the indeterminate loader rather than estimating. Keep labels short enough for the Save dialog, use basenames and compact codec names, and omit redundant import/export wording. New or changed edit paths must include regression tests for their progress sequence, cancellation, and cleanup behavior.

## Commit & Pull Request Guidelines

Recent history uses short, imperative, feature-focused subjects, for example `Add keybinds menu` and `Be able to cancel processing file`. Keep each commit scoped to one coherent change. Pull requests should explain user-visible behavior, list verification commands, and link relevant issues. Include a terminal screenshot or recording when layout or interaction changes.
