# Repository Guidelines

## Project Structure & Module Organization

This repository builds a Rust 2024 library, `reel_tui` (`src/lib.rs`), and one binary, `reel` (`src/main.rs`), on top of it. The library exists so integration tests under `tests/` can drive the same code the binary does. Keep responsibilities aligned across modules:

- `src/lib.rs`: Module declarations only; the crate root shared by the binary and the integration tests.
- `src/main.rs`: Entry point, worker spawning, terminal setup, and the top-level event loop. Deliberately thin — anything testable belongs in the library.
- `src/cli.rs`: Argument dispatch (`--help`, `--version`, the target directory) before the terminal is touched, so informational and usage-error output stays script-friendly.
- `src/config.rs`: The user's `config.toml` — worker-pool sizes, the desktop-notification switch, and the timing page's frame cache (`[preview] cache_tracks`, `[preview.prefetch] enabled`/`network`) and scrub playback (`[preview.playback] fps`/`pad`). `pad` is seconds as a float, so it is read through `Duration::try_from_secs_f64` — `from_secs_f64` panics on a negative, which a hand-written config file can hold — and NaN is rejected *before* the clamp, since `f64::min` answers with the other operand for it and a `pad = nan` would otherwise clamp to the maximum. `MIN_PLAYBACK_FPS`, `MAX_PLAYBACK_FPS` and `MAX_PLAYBACK_PAD` are public because the timing page's preview-settings popup adjusts the same two values for the session and must stop at exactly the limits a config file is held to, rather than at a second copy of them that can drift.
- `src/requirements.rs`: The external tool floors, enforced at startup. See **External Tool Floors** below.
- `src/input.rs`: Key handling (`handle_key` and friends): the mapping from a `KeyEvent` to an `App` mutation.
- `src/app.rs`: Application state, navigation layer management, probe/edit event dispatching, and persistent cache integration. Also holds `PreviewSettings`, which is both the timing page's cache policy *and* the five knobs the preview-settings popup (`:`) adjusts for the session — speed, loop, sound, padding, frame rate. **The popup mutates `PreviewSettings` in place and never writes to disk**: `config.toml` stays the defaults, `preview_defaults` keeps the copy `main` supplied, and `r`/`R` restore from that rather than from `Config::default()` — otherwise `r` on a user who set `fps = 24` would hand them 30 and look like a bug. The popup holds a cursor and nothing else, so what it shows is always what a playback would actually be done with rather than a copy taken when it opened; there is nothing to commit and nothing to discard. **No dialog may be raised over a running or decoding playback** (`App::playback_in_progress`): a span's pixels reach the terminal through its own image protocol rather than through the cell buffer a dialog is drawn into, so a popup opened over one is painted once and wiped by the next frame — open, swallowing every key, and invisible. There is no z-order that fixes this, so the two are kept apart instead: a dialog the user asked for is refused (`:` and `?` on the timing page), while one that raises itself — the conflict notice — stops the playback, since it cannot be refused. **The still frame is kept apart from a dialog by the same rule, drawn from the other end**: `render_sync_preview` leaves the picture out for as long as any dialog is up. The image widget writes its escape sequence into the pane's first cell and marks every other cell it covers *skipped*, and a skipped cell is never re-emitted by the diff — so a dialog that *shrinks while open* (a dropdown closing, the help panel going away) hands back cells nothing will ever paint over, and the border it drew stays on screen around the smaller dialog: the popup drawn twice, at two sizes. Opening and closing one was only ever safe by accident, because `dim_backdrop` restyles the cell the escape sequence lives in and so forces the picture to be re-sent; standing the picture down for the dialog's whole life extends that to every shape it takes in between. Do not "fix" this by drawing the image under a dialog again — the artifact is invisible to `TestBackend`, since the halfblocks protocol the harness uses writes ordinary cells and skips nothing, which is why `a_dialog_over_the_preview_should_take_the_picture_down_rather_than_sit_on_it` asserts the *rule* (no image cells while a dialog is up) rather than the artifact.
- `src/staging.rs`: Staged edits and in-flight batch state (`StagedEdit`, `BatchState`), the shape a save is dispatched and reported through.
- `src/ui.rs`: Ratatui rendering, split layout rendering, stream detail popups, and status indicators (including `[NET]` badge). The preview-settings popup reuses the shared `SettingsDialog` with no text entry and no help panel, and marks a row as *changed* when it differs from what `config.toml` asked for. Speed, padding and frame rate are `setting_line` plus the same `dropdown_line` children every other settings popup opens, so `Enter` opens and commits and `Esc` backs out one level. **The two switches are `toggle_line` instead**, because both answers fit on the row and opening a list to choose between them would hide the answer in order to ask the question; `Enter` flips it and `h`/`l` pick the left or right button (setting rather than flipping, so key repeat lands somewhere instead of oscillating). `h`/`l` are bound *only* there — on a dropdown row a value is chosen from a list, the way it is in every other settings popup. `toggle_line` is built from `action_option`, the button component the three confirm dialogs already use; that takes a `Style` rather than a `focused` flag so both kinds of row can style their buttons through `choice_style`, which is where a button, a dropdown row and a field value all agree on what "chosen", "changed" and "inert" look like. **Every list in this popup runs descending** — fastest, longest, highest first — and `PlaybackSpeed::STEPS` is stored in that order too, because one order for the data and the display is what stops the list and the cursor disagreeing about which end is which. `K` opens the same help panel the other settings popups have (`preview_field_help_text`); its five rows make it the shortest dialog in the application, so it is the one a long explanation overruns first — `every_help_text_should_fit_the_panel_it_is_drawn_in` covers it along with the rest. `playback_settings_badge` puts the same answer in the preview pane's *title* (`Preview · 0.5x · loop · muted`) rather than on the timing page's status row, which already carries one message at a time and where "Preparing playback…" is the one worth reading while a span decodes. It names only speed, loop and sound: padding and frame rate change what a playback costs rather than what it looks like, and a title listing all five would be longer than most panes are wide.
- `src/files.rs`: Directory scanning, file tree nesting, and adaptive filesystem monitoring.
- `src/framecache.rs`: The on-disk cache of rendered preview frames, at `$XDG_CACHE_HOME/reel-tui/preview_frames/{media_key}/{cue_key}.jpg`. Content-addressed with 128-bit FNV-1a: `media_key` covers the media file, its length and mtime, the size frames are rendered at, and `CACHE_FORMAT_VERSION`; `cue_key` covers the **staged subtitle file** — the exact bytes handed to libass — and the cue's timing, which the staging is retimed away from. Not the cue's text: two ASS cues can read the same words in different styles and draw differently. An edited cue simply misses and is re-rendered, with no invalidation logic anywhere. **The two-level path is the eviction policy, not tidiness.** What the user opens is a *track*, and a track missing some of its frames is re-rendered on every visit, so the unit of eviction has to be the unit of use: `prune(tracks, open)` deletes whole media directories, least recently used first, and never the open one. Ranking is by the `.used` marker's mtime (`touch`), so a fully cached track — the ideal case, where the pass renders nothing — does not age out under tracks rendered once. The directory *is* the index, which keeps the grouping without a side file to corrupt or a lock to take. Bump `CACHE_FORMAT_VERSION` when a stored frame stops meaning what it did; that orphans whole directories which then age out, instead of leaving files whose names collide with live keys. Frames are **JPEG** (`FRAME_EXTENSION`), not PNG: ~90 KB at 1080p against ~2 MB for a *smaller* PNG. Resolves its directory through `DiskCache::cache_dir()`, never from the environment, so both test redirections apply. Pure filesystem and hashing.
- `src/probe.rs`: Asynchronous `ffprobe` worker thread, media metadata parsing, and tuned probing flags (`-probesize`, `-analyzeduration`).
- `src/edit.rs`: Asynchronous `ffmpeg` remuxing, track reordering, container conversion, progress reporting, cancellation, and cross-filesystem transaction publishing (`move_or_copy_file`).
- `src/subtitle.rs`: Subtitle stream inspection, sidecar file matching, format conversion, language tag translation, and OCR/libass capability detection (`ToolCapabilities`). `ToolCapabilities` tracks `ffmpeg_decoders` separately from `ffmpeg_encoders` because the timing page *reads* where the rest of the program *writes*, and a build ships plenty of one without the other. `preview_blocked(format)` is the timing page's pre-flight gate: it refuses before the page opens, so a missing tool reads as a refusal naming the tool rather than a page that loads, sits on its loader, and fails.
- `src/cue.rs`: Cue-level subtitle data — SubRip and ASS parsing into individual cues (`parse_srt`, `parse_ass`), timeline lane packing, and the mapping from cue times to terminal columns. ASS parsing also yields the `AssScript` header its cues are drawn by, and `retimed_dialogue` rewrites one cue's line for the preview's staged file. No dependency on `App`, `ratatui`, or subprocesses.
- `src/sync.rs`: State for the subtitle timing page (`SubtitleSyncState`): which cues a track holds, which is selected, the small window of frames encoded and ready to draw (the selected cue and up to `NEARBY_FRAMES` either side — `window_radius()` is the actual reach, see below), how far the background frame pass has got (`WarmState`), why a frame cannot be drawn at all (`PreviewSupport`), and the scratch directory that is released when the page closes. **`PreviewSupport` and `frame_error()` are split by permanence, and the split is the point**: a condition that cannot change while the page is open (this FFmpeg cannot burn subtitles in, or the terminal has no image protocol) is a `PreviewSupport` reason drawn in the preview pane, while a single cue's render failure is `frame_error()` on the status row. Putting a per-cue failure in the pane would reintroduce the text that flashed there on every cursor move, which is why `frame_error()` is keyed on the selected cue rather than exposed as a field. **The window is budgeted, not fixed**: `window_radius()` takes `NEARBY_FRAMES` as a ceiling and shortens it to fit `preview::FRAME_WINDOW_BUDGET`, because a `Protocol` holds the bytes the terminal is going to be sent rather than the picture — kitty and iTerm2 hold the frame's pixels as base64 RGBA and sixel about a byte a pixel (`preview::frame_bytes_per_cell`), which is tens of megabytes for a full window on a large pane. Floored at one either side: a window of nothing puts the worker round trip back on every cursor move, which is what the window exists to remove. `prune_frames`, `nearby_frame_targets`, and `has_missing_nearby` all use the same radius, or the page would render frames it immediately discards and ask for them again. Also holds the scrub playback (`PlaybackState`, `Playback`), whose one subtlety is **which page movements stop it**: the cursor landing on another cue and a new track arriving do (`select_cue`), because a span playing under a line it is not about reads as the timing being wrong; a *pane resize* does not, and must not — announcing the playback is what puts "Preparing playback…" on the status row, and that row comes out of the preview pane's height, so a playback stopped by a resize is stopped by the act of saying it is starting, every time, on any page whose background pass has finished. The frames absorb it instead: they hold pixels, and `Playback::advance` encodes for whatever cell area the pane has become. **`Playback::position` multiplies by the span's speed**, because frames are `1 / fps` apart in *output* time and the playhead answers in *media* time — without the factor the mark on the timeline would crawl at the speed the picture is playing at and read as the cue being mistimed, which is the one thing this page must never say wrongly. A looping playback re-opens its `AudioSource` and resets to frame zero where a non-looping one returns `PlaybackStep::Finished`; the frames are already in memory, so a repeat runs no `ffmpeg`, and a span holding no frames still ends rather than opening a device per iteration of the event loop forever.
- `src/preview.rs`: The timing page's four background workers — reading a track's cues (see **Subtitle formats the timing page reads** below), grabbing the video frame at the selected cue with that cue burned in plus encoding the cues either side of it from the cache (`FrameRequest`'s `wanted` and `nearby`), and rendering the rest of the track's frames behind them with scoped threads over contiguous slices — half the machine's cores, floored at 1 and capped at `MAX_WARM_WORKERS` (3), because a fixed three cost the *interactive* grab +157% latency on a dual core. **Each warm worker stages its cue under its own name** (`warm_cue_file(n)`, distinct from the interactive `CUE_FILE`): two sharing one staged `.srt` would overwrite each other between the write and the burn, and the frame would carry another cue's line under the right cache key — invisible to any assertion about keys, counts or files, which is why the tests for it compare rendered bytes. Frames are rendered at a fixed size derived from the source, capped at 1080p by `MAX_FRAME_PIXELS` (not the pane's size, which changes), and cached through `framecache.rs`. The grab is `mjpeg -pix_fmt yuvj420p -q:v 2`; the pixel format is load-bearing, since the mjpeg encoder refuses the limited-range YUV most video actually is. The fourth worker is the scrub playback: one `ffmpeg` decodes a whole span straight to raw `rgb24` (an accurate seek costs the same whether one frame comes out of it or four hundred), with the sound as a second output of the *same* pass so picture and sound describe the same stretch of media by construction. Three things there fail invisibly: `scale` is a literal `W:H` with **no** `force_original_aspect_ratio`, because the output is sliced by `width * height * 3` and a frame one row short shears every frame after the first rather than cropping — the proportions are kept by `playback_cells` choosing the size from the source's aspect ratio instead; the cue is staged by `CueStyle::stage_between` at its place *inside* the span rather than covering it, which is the opposite of what the still grab wants and which every assertion short of the pixels still passes; and the sound goes to a **file**, not a second pipe, since two pipes into one `ffmpeg` deadlock the moment either reader falls behind — which means every playback of a page writes the same name in the same workspace, so a run that asks for no sound (muted, or media with no audio track) must both **clear that file before the decode and skip reading it after**, or the page plays the *previous* cue's sound under this one's picture. Playback frames are never cached — `framecache` keys on a cue and evicts whole tracks, and a run of frames keyed on time has no business in it — so the frame rate is what gives when a span will not fit in `PLAYBACK_BUDGET` (`affordable_fps`), since span length and terminal size are the user's. **`PlaybackSpeed` is applied entirely by that one decode** — `setpts` on the picture, `atempo` on the sound — which is what keeps the two describing the same stretch of media and leaves `audio.rs` knowing nothing about speeds. Three details there are load-bearing and none of them is visible in a frame count: `setpts` sits *behind* `subtitles`, because libass lays the text out against the source's own timestamps and a retimed stream moves the cue out from under the frames it belongs on, and *ahead* of `fps`, so the rate filter yields that many frames per second of output rather than per second of media; a quarter speed emits `atempo=0.5,atempo=0.5`, since one filter cannot halve a span twice and `ffmpeg` refuses `atempo=0.25` outright; and `affordable_fps` is charged the **stretched** span (`span / speed`), or a slow playback quietly overshoots the budget by the speed factor. **`source_capped_fps` runs before that budget**, because the `fps` filter *duplicates* frames to reach a rate the source does not hold: a 24 fps film asked for 60 comes back two and a half times the size for the same picture, and the waste is charged to `PLAYBACK_BUDGET` as if it were real. Scaled by the speed for the same reason the budget is — a second of output covers `speed` seconds of media, so half speed has half the source's frames to give it — and skipped entirely when ffprobe will not state a rate, since guessing one would make a playback choppier for a file that was merely unreadable. **The popup is capped by the same ceiling** (`App::playback_fps_choices`, `effective_playback_fps`): a dropdown offering a 23.976 fps track sixty frames a second states a rate that cannot happen and gives the reader no way to tell. **The list is capped at the speed-scaled ceiling, so it shortens as the speed drops** — a 24 fps film offers 24/15/10/5 at normal speed and 6/5 at a quarter of it. Leaving the full list there would offer four rows that all play identically, which is the same defect as offering 60 on a 24 fps film one level down; the list getting shorter is the honest signal, not a side effect. The ceiling is rarely one of the curated rates, so `effective_playback_fps` is *merged* into the list rather than only filling in an empty one — it is what the row will play at, so it has to be selectable and `preview_choice_cursor` has to be able to find it. The row is never disabled, because a rate *below* the ceiling is still a real choice at any speed: it is the escape hatch for a terminal that cannot keep up over ssh or inside tmux, which is exactly where slow playbacks live. The *setting* is left alone by both caps, so a detour through quarter speed — or a visit to a 24 fps film — does not cost the user the 60 they chose. One consequence worth knowing: with the list capped this way, slowing a playback down costs no extra memory at all, since `(span / speed) x fps` is at most `span x source_fps` whenever `fps` is under the ceiling. At exactly normal speed neither filter is emitted, so the default command is byte-identical to the one this was added to. **The span is decoded at `playback_pixels`, which is the terminal's own cell size per cell, taken off the picker.** The frame is then drawn as pixels through that same picker — which is the only way a burned-in subtitle is *readable* rather than merely present. There is no cells-and-colours fallback anywhere in this path, and there must not be: `preview::drawing_picker` refuses a halfblocks picker at startup (see **Previews Require a Real Image Protocol** below), so a page that exists is a page that can draw.

**`playback_cells` and `playback_pixels` apply the cell's aspect ratio in opposite directions, and the two must cancel.** A cell is roughly twice as tall as it is wide, so a 16:9 picture is nothing like 16:9 *in cells*: `playback_cells` divides by that ratio to pick the cell area, and `playback_pixels` multiplies it back by the font to pick the decode size. Both take the ratio from the font rather than from a constant two, which is what makes the product come back to the source's proportions exactly — a cell that is 8x17 rather than a tidy 10x20 would otherwise stretch every frame by a seventeenth. Dropping either factor, or applying one twice, distorts the picture by about four and no assertion about counts, keys or command lines notices. Because they cancel, `PlaybackFrames::pixels` *is* the picture's true shape, which is what a resize re-fits against; there is no separate record of the media's own size and none is needed. The three figures that do have to agree — `pixels`, `cells`, `picker` — are gathered into `SpanShape` and travel with the span, so the decode resolution and the encoder are provably one decision. That is also why the playback worker clones the picker inside `spawn_preview_workers`' `Some(picker)` arm: a decoded span without a picker to draw it with is then not a state that exists. Deliberately does **not** route through `edit.rs`, so a read-only preview never writes `edit_errors.log`.
- `src/audio.rs`: Sound for the timing page's scrub playback, and the clock the picture is driven from. **The sound is the clock**: nothing schedules a frame, the audio device is asked where it has got to and the frame index is derived from that (`frame_index_at`), so there is no second clock to drift against. **Counting the samples written to the device is the wrong clock and the mistake this module exists to prevent** — a callback fills a buffer the device plays one period later, so a written-sample counter *leads* the sound by the device latency: constant, silent, tens of milliseconds, and indistinguishable on screen from the subtitle actually being early. `PlaybackClock::anchor` therefore takes cpal's `playback`-minus-`callback` lead and re-anchors every callback, leaving wall time to interpolate across one buffer period. `PlaybackClock` names no audio library, which is what lets the part that has to be right be tested on a machine with no sound card. `SilentOutput` is **production code, not a test double**: a machine with no device and media with no audio track take it, and the tests get it because it is that path — and so does a playback the user muted, which asks for no sound from the decode at all rather than turning a device down. `AudioSource` is the second seam, and it exists for looping: a `cpal` stream plays its buffer once, so going round again means opening another output rather than rewinding one. `sync::Playback` therefore holds a source rather than an output, and a repeat costs a device open rather than another `ffmpeg` run. The one thing in here that cannot be tested through a device is `span_slice`, hence its being a function — `handed_over` counts whole buffers of device *time* rather than samples copied (freezing it at the last sample walks the reported position backwards), so it runs past the end of the span, and `slice[n..n]` panics for `n` past the end even though the range is empty.
- `src/notification.rs`: Best-effort desktop notifications when a save finishes while the terminal is unfocused.
- `src/mount.rs`: Network mount detection via `/proc/mounts` (NFS, SMB/CIFS, SSHFS, Rclone, Ceph, etc.) and `REEL_NETWORK_MODE` environment variable overrides.
- `src/cache.rs`: Persistent on-disk probe metadata cache (`DiskCache`) stored at `$XDG_CACHE_HOME/reel-tui/probe_cache.json`.

Unit tests live beside their implementation in `#[cfg(test)] mod tests` blocks. End-to-end tests live in `tests/e2e.rs` with helpers in `tests/e2e/`. Release publishing is defined in `.github/workflows/publish.yml`.

## End-to-End Test Suite

`tests/e2e.rs` drives the real application: it replays the `main.rs` event loop in-process, feeds synthetic `KeyEvent`s through the same `handle_key`, renders through the same `ui::render` into a `TestBackend`, and runs genuine `ffprobe`/`ffmpeg` subprocesses against real files. Nothing in the crate is mocked; only crossterm's terminal setup and byte decoding are bypassed.

- It is a **separate cargo test target with `test = false`**, so ordinary `cargo test` does not run it; use the restricted execution rules below.
- **Comprehensive e2e coverage is the target, and the current gaps are testing debt to fill incrementally.** Whenever work touches a functional area that lacks an overarching scenario in `tests/e2e.rs`, add one as part of that work.
- **Every new or materially changed functional behavior must be covered by at least one overarching scenario in `tests/e2e.rs`.** The scenario must exercise the behavior through the real application workflow independently of module-local unit tests and make meaningful assertions about the observable result. Coverage overlap is explicitly welcome and does not waive either layer. Purely visual styling or layout changes do not require their own e2e scenario, but do require focused rendering/unit coverage.
- **Tests never skip.** Do not use `#[ignore]`, conditional early returns, environment-based success paths, or any other mechanism that reports an unexecuted test as passing. Required programs, codecs, language data, and other external capabilities are test-environment prerequisites; fail immediately with an actionable missing-prerequisite message.
- **E2E execution is deliberately restricted.** Run an individual scenario only while creating or directly changing that scenario. Run the complete e2e suite only once as the final verification immediately before merging a branch. Do not run e2e tests during ordinary implementation, routine verification, or on every edit. Minutes of wall clock for the final suite is fine: use real codecs, containers, subprocesses, and OCR rather than reducing fidelity for speed.
- When a regression scenario comes from a failure in `~/.cache/reel-tui/edit_errors.log`, quote that log line in its doc comment. That log is the first place to look when hunting for an edit regression worth locking in; UI and workflow regressions need not originate there.
- Fixtures are built by `tests/e2e/fixtures.rs` over `lavfi` sources, parameterised by codec and container. Codec/container realism is the point: the bugs this suite exists for come from combinations like `subrip` into MP4 or `mov_text` into Matroska, which the simpler `ffv1`/`pcm_s16le` unit fixtures cannot express.
- **Scenarios that render preview frames must take `harness::frame_cache_lock()`.** `XDG_CACHE_HOME` is process-global, so every scenario in the binary renders into one frame cache, and the timing page prunes that cache to whole media directories at the start of every background pass — `a_full_cache_should_evict_whole_tracks_and_never_the_open_one` deliberately prunes it to a single track. Run in parallel without the lock, the scenarios delete each other's frames: one walking a cue list waits forever for a frame another has just evicted, which reads as a hang in the feature rather than as interference. It is not a wall-clock cost — taking it took the suite from 92 s to 18 s, because the thrashing was re-rendering evicted frames.
- The harness redirects `XDG_CACHE_HOME` to throwaway storage, so runs never touch the user's real probe cache or failure log. The unit-test binary is covered separately: `DiskCache::cache_dir()` returns throwaway storage under `cfg(test)` (`src/cache.rs`). **Both halves are load-bearing** — without them a test run rewrites `~/.cache/reel-tui/probe_cache.json` with `/tmp` fixture paths and fills `edit_errors.log` with deliberately-failing test edits, which is exactly the log this file tells you to read first. Never add a test that resolves the real cache directory.
- **Write tests that would notice.** A test that passes against broken code converts an unchecked path into a checked-looking one, so assert the observable result rather than the fact that something ran. A feature-level e2e scenario need not reproduce every defect in that feature; focused regression coverage belongs in the unit suite.

## Subtitle Formats the Timing Page Reads

Every format ends at the same place — a SubRip file `cue.rs` parses — and differs only in how it gets there. `preview::prepare` owns the dispatch; `ToolCapabilities::preview_blocked` refuses the rest before the page opens.

| Format | Road to the cue list |
| --- | --- |
| SubRip | `-c:s copy` out of the container, or the sidecar read where it lies. Parsed by `cue::parse_srt`. |
| ASS | **Also `-c:s copy`, and that is load-bearing** — see below. Parsed by `cue::parse_ass`. |
| WebVTT, MOV Text | Transcoded to SubRip — on the way out of the container for an embedded track (`-c:s subrip`), in a second `ffmpeg` pass for a sidecar. Needs an `ffmpeg_decoders` entry, not an encoder one. |
| TTML, PGS, VobSub | Refused. TTML has no FFmpeg decoder at all (there is an encoder, which is not the same thing); PGS and VobSub carry pictures rather than text. |

**ASS is never transcoded, because a transcode discards what makes previewing it worth doing.** An ASS cue *names* a style rather than carrying one, and positions itself against the script's declared `PlayResX`/`PlayResY` rather than against the video. So the page keeps three things a SubRip track has no equivalent of:

- `Cue::dialogue` — the cue's original `Dialogue:` line, verbatim. `Cue::text` is what the *reader* needs (markup stripped, `\N` unfolded) and this is what the *renderer* needs; for ASS they are not the same string.
- `CueStyle::Ass { header, events_format }` — the file's `[Script Info]` and `[V4+ Styles]` verbatim, plus the `[Events]` `Format:` line. Field order is declared per file rather than fixed by the format, so both the parse and `cue::retimed_dialogue` read that line rather than assuming the usual columns.
- `CueSlot` — the staged file's *name*, whose extension libass picks its reader from. A staged ASS script called `.srt` is read as SubRip and every override tag in it lands on the frame as literal text.

**`framecache::cue_key` hashes the staged file, not the cue's text.** That is what makes the key provably complete: the picture is a pure function of the media, the moment seeked to, and the file handed to libass — `media_key` covers the first, the cue's timing covers the second, and the staged bytes cover the third. Hashing the text was right while SubRip was the only format, where text *is* the staged file; it stops being right the moment two cues can read the same words in different styles and draw differently.

**The staged filename and the extraction's `-c:s` have to agree.** `ffmpeg` picks its muxer from the extension, so a WebVTT track transcoded to SubRip and written to `cues.vtt` fails on a codec the muxer will not take. `extracted_format` is the single answer both halves read, and the mistake is invisible in either half alone — which is why an e2e scenario covers it rather than only a unit test of the command.

**Test the styling on rendered bytes.** A preview that lost an ASS track's styling still parses the right cues, caches the right number of frames, and draws the right list — every assertion short of the picture passes. `an_ass_track_should_preview_with_its_own_styles_rather_than_libass_defaults` therefore gives two cues identical words in different styles and compares the cached JPEGs, the same reason the warm-worker staging test compares bytes.

## External Tool Floors

`src/requirements.rs` holds the minimum versions, each measured rather than guessed. Do not lower one without re-measuring; each is load-bearing.

- **FFmpeg 8.1** (`ffmpeg` *and* `ffprobe`) — enforced at startup, refusing to launch below it. `n8.1` is the first release containing FFmpeg commit `e59d964a3c`, which taught the `mov` demuxer to read the ISO-BMFF `name` atom. Below it `ffprobe` reports MP4/MOV track titles as absent, so a remux erases every title, `apply_edits` writes the erasure out as `title=`, and `validate_result` compares absent against absent and passes it. No flag works around it — the muxer never receives a title the demuxer did not parse. The e2e suite otherwise passes on 5.0.1 through 8.0.1, so the floor is entirely about this. Also verified green on **9.0.1**, the whole suite, so the major version bump needs no ceiling.
- **seconv 5.1.0** — gates subtitle conversion and OCR, not startup. 5.0.0 cannot read a VobSub `.idx` ("Unable to determine subtitle format"). **Cannot be version-gated**: the 5.1.0 build reports `5.0.0` from `--version`, so `subtitle::seconv_is_supported` probes the `--help` listing for `--no-vobsub-isolate-colors` instead. Also needs `libicu` present, or it aborts in `Bootstrap.Initialize`.
- **Tesseract 4.0** — gates OCR only. Verified working on 4.0.0, 4.1.1, and 5.3.x. 3.x is unreachable regardless: `seconv` needs a newer glibc than any distribution shipping it.

- **`pkg-config` and the ALSA headers** — a *build* dependency, not a runtime one, and not versioned. `cpal` pulls in `alsa-sys`, whose build script is a bare `pkg_config::probe_library("alsa")`, so without them the crate does not compile and no suite runs at all. A machine with the headers but no sound *device* is fine: `audio::open` falls back to `SilentOutput`, which is the same production path a user without a sound card takes, so CI needs no audio hardware.

CI installs these from `.github/actions/media-tools`, never from the runner's distribution packages — `ubuntu-latest` ships FFmpeg 6.1.1, which is below the floor. `.github/workflows/ci.yml` runs both suites on every push and pull request to `main`; `publish.yml` runs on release tags only and is not a substitute for it.

## Previews Require a Real Image Protocol

The timing page exists to judge a subtitle against the picture it is burned into, so a terminal that cannot show the picture cannot answer the question the page is for. `preview::drawing_picker` therefore discards a `Halfblocks` picker at startup, in `main.rs`, and `spawn_preview_workers(None)` follows from that: no frame worker, no background cache pass, no playback. The page still opens and still reads the cue list — that half works — and says `PreviewSupport::NoImageProtocol` in the preview pane rather than leaving it blank, since silence there is indistinguishable from a slow render.

This matters because `Picker::from_query_stdio` reports halfblocks for *every* terminal that answered nothing, so without the refusal the fallback would be the common case: full-screen terminals rendering, caching and playing hundreds of frames that arrive as coloured mush, with the user judging subtitle timing by them. Two coloured half-cells cannot carry text. Terminals that do work are those offering kitty graphics (kitty, Ghostty, WezTerm, Konsole), iTerm2 (iTerm2, WezTerm, Konsole, mintty), or sixel (foot, WezTerm, mlterm, xterm, contour, Windows Terminal).

**The e2e harness deliberately passes a halfblocks picker anyway** (`Harness::start`), because it is the only protocol `TestBackend` records as cells with symbols and colours — kitty, sixel and iTerm2 write escape sequences the buffer never stores, so no assertion could see the picture. Everything the page does with a frame is protocol-agnostic; only the encoder differs. `Harness::start_without_image_protocol` is the other side, and `a_terminal_with_no_image_protocol_should_say_so_rather_than_draw` is what holds the refusal in place.

## Adaptive Filesystem & Performance Architecture

`reel-tui` automatically detects whether the target directory resides on a local disk or a remote network mount (NFS, SMB, etc.):

- **Directory Monitoring**: Local directories use a 1-second reconciliation interval; network mounts use an adaptive 10-second interval to eliminate network stat thrashing.
- **Persistent Probe Cache**: Media metadata is cached on disk in `$XDG_CACHE_HOME/reel-tui/probe_cache.json` indexed by path, file length, and mtime. Opening `reel` on network shares loads previously probed files instantly.
- **Fast Probe Flags**: Remote media probing uses `-probesize 2000000 -analyzeduration 3000000` to prevent deep network seeking.
- **Local Scratch Remuxing**: When remuxing on network mounts, intermediate work files write to local fast storage (`/tmp/reel-tui-scratch`) before performing a single final stream publish to destination.
- **Preview Frame Cache**: Opening the subtitle timing page renders every cue's frame in the background and caches it on disk, so revisiting a cue — or re-opening the page — costs a decode rather than an `ffmpeg` seek. Bounded by whole media files (`cache_tracks`, default 10) rather than by bytes, because a byte budget can bisect a track and half a track is re-rendered on every visit. Off by default on network mounts, where a feature-length track is a thousand-odd accurate seeks across the network; the page says so in its status row rather than leaving the absence unexplained.
- **Ready Preview Frames**: On top of the disk cache, the page keeps the selected cue's frame and the ones either side of it *encoded* in memory, so moving the cursor draws a picture in the same pass that handled the keypress rather than after a round trip to the worker. `FRAME_DEBOUNCE` therefore applies only to a cue that would have to be rendered — one already in the frame cache is asked for immediately, since it costs a file read rather than an accurate seek. **A debounced cue is held back from the dispatch, not the dispatch itself**: the neighbours travelling with it are cache-only by construction, so returning early would strand the cheap work behind the expensive work and hand back the round trip the window exists to remove. `clear_nearby_request` is what makes that safe — the held-back grab is deferred, not answered, and still goes out when the debounce expires. In the other direction, `apply_warming` refills only when `has_missing_nearby()`, since the background pass reports ten times a second and a full window has nothing to fetch. That gate is deliberately **not** "has the pass reached the window": the warm workers render contiguous slices in parallel, so `done` counts frames rather than describing a prefix. The preview pane draws nothing when it has no frame; it never substitutes the cue's text, which flashed on every cursor move. The one exception is a preview that can *never* work — no libass, or no image protocol — which the pane says once and keeps saying, since silence there is indistinguishable from a slow render.
- **Environment Overrides**: Set `REEL_NETWORK_MODE=1` (or `0`) to manually force or disable network performance tuning.

## Build, Test, and Development Commands

- `cargo run`: launch the TUI against the current directory. Ensure `ffmpeg` and `ffprobe` are available in `PATH`.
- `cargo build`: compile a debug binary.
- `cargo build --release`: compile an optimized release binary.
- `cargo install --path .`: install or replace the `reel` executable in `~/.cargo/bin/reel`. Always run this after making changes.
- `cargo test`: run all module-local unit tests. Excludes the e2e suite.
- `cargo test --test e2e <scenario> -- --exact`: run one scenario only while creating or directly changing that scenario.
- `cargo test --test e2e`: run the complete end-to-end suite only as the final pre-merge gate. Its required `ffmpeg`/`ffprobe` programs and encoders must be installed; missing prerequisites fail the suite.
- `cargo fmt --check`: verify standard Rust formatting.
- `cargo clippy --all-targets -- -D warnings`: run strict linting used by CI. Note this does **not** cover `tests/e2e.rs`, whose target sets `test = false`; lint that one with `cargo clippy --test e2e -- -D warnings`.
- `cargo publish --dry-run`: validate packaging without publishing.

## Coding Style & Naming Conventions

Use `rustfmt` defaults (four-space indentation) and keep Clippy warning-free. Follow Rust conventions: `snake_case` for functions, variables, and modules; `PascalCase` for structs and enums; `SCREAMING_SNAKE_CASE` for constants. Prefer small, responsibility-focused functions and propagate recoverable failures with `anyhow::Result`. Preserve terminal cleanup guarantees and keep blocking `ffmpeg`/`ffprobe` work off the UI event loop.

**No inline control help text**: never add a hint/help line (e.g. "↑↓ select · Enter apply") to a dialog, popup, or view's render function, no matter how new or small. All keybinding help lives solely in the global keybindings popup (`?`, `Dialog::Keybindings`/`keybindings_text()` in `src/ui.rs`). If a new view's keys aren't already covered by that popup's generic entries, extend `keybindings_text()` rather than adding local hint text.

## Testing & Reinstallation Guidelines

Add tests in the module affected by the change, using descriptive behavior names such as `cancelled_edit_preserves_original`. Use temporary paths for filesystem cases and deterministic JSON fixtures for probe parsing. No test in any suite may be ignored or conditionally skipped. During ordinary work, run `cargo fmt`, `cargo clippy --all-targets -- -D warnings`, and `cargo test`; reserve the complete e2e suite for the final pre-merge gate.

### Coverage and Regression Policy

- Maintain a project target of at least **90% measured line coverage**, and prefer coverage comfortably above 90%. Measure branch coverage as well when the installed Rust coverage tooling supports it, and improve weak branch coverage rather than relying on the line percentage alone.
- New or modified production paths must have **100% line and branch coverage from module-local unit tests**. E2E coverage is a separate requirement and does not substitute for unit coverage. Existing uncovered code remains debt, but touching it means covering the affected paths completely.
- Every bug fix must include a focused module-local regression unit test that fails before the fix and passes afterward. Reproduce the complete failure mode, including effects on neighboring or untouched data; do not test only the value directly changed by the user. The affected functional area must also have an overarching e2e scenario; add one if it does not, but that scenario need not reproduce the exact defect.
- Cover meaningful success, failure, cancellation, validation, and transaction/rollback paths. For FFmpeg and ffprobe behavior, include integration tests using small deterministic media fixtures when unit tests cannot verify the real command semantics.
- Treat coverage as a diagnostic floor, not proof of correctness. Do not inflate it with assertion-free tests, broad exclusions, or tests that execute code without validating observable behavior. **Covering unreachable code is inflation too**: before writing a test to reach the coverage bar, check that the application can actually reach the path. If it cannot, delete the path instead of testing it, and say so.
- Report the unit-test coverage method and totals with completed ordinary changes. Report merged unit-and-e2e coverage only at the final pre-merge gate. If coverage cannot be measured in the current environment, state that explicitly rather than estimating it.
- **Measuring final pre-merge coverage.** Branch coverage needs `-Z coverage-options=branch`, which only nightly `rustc` accepts, so it runs under `cargo +nightly llvm-cov --branch`. Because the unit and e2e suites are separate targets, the merged commands below run the complete e2e suite and therefore must only be used immediately before merging a branch:

  ```sh
  cargo +nightly llvm-cov clean --workspace
  cargo +nightly llvm-cov --no-report --branch            # unit tests
  cargo +nightly llvm-cov --no-report --branch --test e2e # e2e suite
  cargo +nightly llvm-cov report --branch --summary-only
  ```

  A plain `cargo llvm-cov` run silently excludes the e2e suite (its target sets `test = false`), which understates `edit.rs` in particular — the remux paths it covers are the ones only e2e reaches.

  Do **not** set `LLVM_COV`/`LLVM_PROFDATA` to the system `/usr/bin` binaries for these runs: the Arch system LLVM is older than nightly's and fails with `raw profile version mismatch`. Rustup supplies matching `llvm-tools` for the toolchain automatically. (That override was only needed back when the machine had no rustup at all.)

  Note that `llvm-cov` counts branches inside `#[cfg(test)]` modules as well as production code, so a test containing loops or `match`es raises the denominator along with the numerator. Treat the per-file trend, not the absolute percentage, as the signal.

**Mandatory Reinstall Step**: After making changes and successfully passing tests, ALWAYS run `cargo install --path .` so the updated `reel` binary is immediately installed to `~/.cargo/bin/reel`.

### Edit Progress Contract

Treat accurate progress reporting as a required part of every Save workflow change. Every blocking subprocess, potentially slow filesystem operation, validation pass, transaction phase, rollback, and cleanup path must emit a concise typed progress phase immediately before doing the work. Use measured phase-local progress only when the underlying operation exposes reliable units; otherwise show the indeterminate loader rather than estimating. Keep labels short enough for the Save dialog, use basenames and compact codec names, and omit redundant import/export wording. New or changed edit paths must include regression tests for their progress sequence, cancellation, and cleanup behavior.

## Commit & Pull Request Guidelines

Recent history uses short, imperative, feature-focused subjects, for example `Add keybinds menu` and `Be able to cancel processing file`. Keep each commit scoped to one coherent change. Pull requests should explain user-visible behavior, list verification commands, and link relevant issues. Include a terminal screenshot or recording when layout or interaction changes. Call out required `ffmpeg` behavior and any compatibility implications. Do not commit generated `target/` contents.
